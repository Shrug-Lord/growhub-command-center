# Firmware-owned active schedules

Command Center stores reusable schedule templates, but CE firmware owns each device's active runtime schedule. Command Center loads a template by pushing the CE schedule contract to the device, then mirrors the firmware-published active device schedule as truth instead of continuously evaluating relay automation itself. Template loads replace the device's active schedule rather than merging into it, so Command Center must warn when loading a template will remove existing active schedule entries that are not represented by the template. This keeps automation running when Command Center, MQTT, or the Command Center host is offline, at the cost of treating local firmware edits as first-class device state; if those edits drift from a named template, Command Center must show the drift and require an explicit user action before saving it back to a template.

After a successful template load, Command Center records the exact compiled physical-outlet CE v3 payload as the expected active schedule for that device, along with the source template identity, template revision, and role mapping used for the load. If the device was already drifted, the confirmed load establishes a new expected active schedule and clears the previous drift, even when the user loaded a different schedule template. Schedule drift is detected by comparing firmware-published active schedule state to that expected active schedule, not by recompiling the current reusable template. This keeps drift detection stable when a template, role label, or role mapping changes after the device was loaded.

Inferred role mappings returned by schedule-load preflight are preview data only. Opening preflight, seeing an inferred mapping, cancelling, or abandoning the flow does not persist role mappings and does not change template deployment state. Command Center persists the role mapping used for a template load only after firmware-published schedule state confirms the load. The first shippable version has no standalone explicit remap action; remapping happens only through loading or reloading a template and firmware confirming the resulting active schedule. A standalone remap action can be reconsidered later if there is a clear user workflow for changing future expectations without changing firmware state immediately.

For schedule-load confirmation and drift detection, Command Center compares the normalized active schedule body from firmware `schedule/state.schedule` against the expected compiled CE v3 payload. Relay mode, `source`, time health, sensor health, warnings, `outlet_status`, and user-facing summaries are runtime or health state and do not count as schedule drift. Normalization prevents JSON field order, outlet order, and numeric formatting differences from creating false drift.

Publishing a compiled schedule creates a pending schedule load, but Command Center does not immediately replace the expected active schedule. The compiled payload becomes the expected active schedule only after a newer firmware-published schedule state confirms the device accepted and owns that active schedule body. If firmware publishes a relevant post-handoff schedule error or confirmation times out, Command Center keeps the previous expected active schedule, preserves any existing schedule drift, and records the load as `rejected` or `timed_out` rather than using an ambiguous failed status.

Loading a schedule does not automatically change the device's relay mode. Command Center publishes the compiled active schedule and preserves the current firmware-owned mode. If the device is already in AUTO, CE firmware evaluates the newly loaded schedule normally. If the device is in MANUAL, the schedule is loaded and persisted but is not actively evaluated until the user explicitly runs `Return to AUTO`. Command Center shows the template as loaded while also showing that automation is paused by MANUAL mode; it does not publish an implicit mode change as part of schedule loading.

The first shippable version does not include a combined `Load and Return to AUTO` action. Schedule loading and relay mode changes remain separate confirmed device actions. After a schedule load confirms while the device is still in MANUAL, Command Center may show `Return to AUTO` as the clear follow-up action, but it does not chain or hide that mode change behind the schedule load.

If a pending schedule load receives neither a matching newer firmware `schedule/state` nor a relevant newer `schedule/error`, Command Center uses the uniform first-ship 15-second confirmation deadline measured from MQTT handoff. A timed-out schedule load leaves the previous expected active schedule unchanged, is not retried automatically, and leaves the UI showing the mirrored firmware state with an explicit retry or load action. Any later matching firmware state updates the current mirror but never rewrites the terminal timed-out action.

For the first shippable version, Command Center allows only one pending schedule-changing action per device. While a schedule load is pending, Command Center disables or rejects additional load-template, load-latest, any future supported clear-schedule action, outlet assignment changes that can clear schedule entries, and mode changes that depend on the pending schedule. This avoids ambiguous confirmation because the CE firmware MQTT contract does not include request IDs.

While a schedule load is pending, Command Center still allows read-only refreshes but blocks time sync, routine relay mode changes, and direct outlet controls until the pending schedule load resolves. Schedule load and time sync both confirm through retained `schedule/state`, and allowing them to overlap would make action attribution ambiguous. An explicit emergency manual all-off action stays available; using it marks the pending schedule load as interrupted so Command Center does not treat later retained state as a clean template-load confirmation.

If the active device schedule still matches the expected active schedule but the source schedule template has advanced to a newer revision, Command Center treats that as a template update available, not schedule drift. Template role label edits are part of that template update state; they do not automatically rewrite existing device mappings' expected label snapshots and do not create immediate label drift across already-loaded devices. Loading the newer revision or explicitly remapping a role establishes the new expected label for that device. Loading the newer revision remains an explicit user action that runs the normal retained outlet-state preflight and full-replacement schedule load workflow. Schedule loading does not rename firmware outlets or publish outlet config as a side effect; if the firmware-owned outlet label differs from the newly expected label after load, Command Center shows label drift and offers explicit `Outlet label repair` or `Label drift acknowledgement`.

Schedule-load preflight blocks on missing, ambiguous, or incompatible outlet assignments because Command Center cannot compile a valid physical-outlet schedule without a safe assignment match. Current Device setup review is also required before schedule loading; outlet label conflicts block Device setup review until the device labels are disambiguated, so schedule-load responses report `device_setup_review_required` with optional context such as `review_blocked_by: "outlet_label_conflict"` rather than treating label conflict as a separate top-level schedule-load blocker. Duplicate labels on outlets assigned None are not outlet label conflicts because unassigned outlets are not valid schedule roles; Command Center may still show them as low-priority setup cleanup. Label drift is a non-blocking warning when the mapped physical outlet still has a compatible assignment. The user may continue loading the schedule and resolve label drift separately with `Outlet label repair` or `Label drift acknowledgement`.

Command Center does not support partial schedule loads for the first shippable version. Every template role must map to a compatible physical outlet before a template can be compiled and loaded. If a template contains an `AC Controller` role and the target device has no compatible AC outlet, the load is blocked instead of dropping that role from the compiled schedule. This keeps the meaning of the reusable template intact and avoids presenting a partially loaded template as if the full plan were running.

Extra assigned firmware outlets that are not represented by the selected template do not block schedule loading. Command Center shows them as non-blocking preflight warnings because the compiled schedule will not include entries for those outlets. If the current firmware active schedule includes entries for those extra outlets, the warning must make the replacement effect explicit: loading the template will remove those active entries from the device.

When schedule-load preflight has no blockers but does have non-blocking warnings, Command Center requires an explicit confirmation before publishing the schedule. Clean preflight may proceed directly, but warning cases such as label drift, extra assigned outlets, active entries that will be removed, existing schedule drift that will be replaced, invalid wall time, or sensor warnings must show a warning summary and require a deliberate `Load Anyway` action. When the target device is already drifted, the warning must state that the current firmware-owned drifted schedule will be replaced by the selected template and that drift will clear only after firmware confirms the load. Remediable warnings should expose their remediation action from the same confirmation flow when available, such as `Sync Time First` for invalid wall time. If the user remediates a warning, Command Center waits for firmware-retained state to confirm the remediation and then reruns preflight before loading.

Before device preflight, a schedule template must have unique assignment and label pairs across its template roles, and each template role must use a non-None assignment. `None` means no equipment role is assigned, so it is valid firmware outlet state but not valid schedule-template content. Two roles may share the same assignment only when their labels differ, such as `Fan` + `Exhaust Fan` and `Fan` + `Circulation Fan`. Two roles with the same assignment and same label make the template incomplete and unloadable until the user gives them distinct labels or removes one role. A role assigned None also makes the template incomplete and unloadable until the user chooses a schedulable assignment or removes the role. This prevents ambiguous or meaningless role mapping and compile behavior before Command Center considers a target device's retained outlet state.

Command Center shows template deployment state from both sides of the relationship. A schedule template detail view acts as the fleet overview for that template, showing each relevant device's loaded revision, schedule drift, template update availability, and explicit load-latest action. A device detail view shows the same relationship from that device's perspective so device operations do not require navigating through the template first.

The first shippable Command Center does not support bulk load-latest actions from the template fleet view. Template deployment state is visible across devices, but each load-latest operation is an explicit per-device action so retained outlet-state preflight, warnings, MQTT publish, firmware confirmation, and failures stay clear. Bulk loading can be added later after the per-device workflow and result reporting are solid.

The first shippable Command Center does not include a remote clear-active-schedule action. The current CE firmware MQTT schedule-write contract rejects empty schedules and does not treat them as clear commands, so Command Center must not fake clearing by publishing an empty schedule. For the first pass, users can load another valid template, use emergency/manual all-off behavior, or clear locally through firmware; a remote clear action can be added later only with a first-class firmware MQTT contract and confirmation path.

If firmware-local UI clears the active schedule, Command Center mirrors the firmware state as cleared but does not automatically clear its expected active schedule record. The cleared firmware schedule is schedule drift from the last confirmed expected active schedule. Command Center should show that the device schedule was cleared locally and offer explicit actions such as reloading the template, acknowledging and unlinking the device from that expected schedule, or saving eligible firmware state as a new template.

If an assignment-changing outlet edit causes firmware `schedule/state` to no longer match the expected active schedule, Command Center does not automatically unlink the device from the expected schedule or source template. The expected active schedule remains the comparison target, the device is marked as schedule drift, and Command Center offers explicit recovery actions such as reloading the template, saving eligible firmware state as a new template, or acknowledging and unlinking the drift. Automatic unlinking would erase the context that explains why the device no longer matches the template deployment.

Schedule drift is independent of relay mode. If firmware-local schedule edits happen while the device remains in AUTO, Command Center mirrors the device as AUTO and drifted; it does not infer MANUAL mode from the schedule mismatch. CE firmware remains authoritative for the active schedule currently running. Command Center notifies the user that firmware-side changes were detected and offers explicit recovery actions such as Reload expected schedule, Save as new template when eligible, or Acknowledge drift.

Schedule drift requires an explicit user reconciliation before Command Center hides or clears it. Drift does not clear merely because the device remains stable, returns to AUTO, reconnects, or continues reporting the same firmware-owned active schedule. Command Center clears drift only after a confirmed schedule load or reload that establishes a new expected active schedule, a successful Save as new template action, or explicit drift acknowledgement/unlinking.

When Command Center first observes a device transition from matching its expected active schedule to schedule drift, it records an informational device activity entry that makes clear the change was detected from firmware-owned state, not caused by a Command Center action. When drift is later reconciled through reload, Save as new template, or acknowledgement, Command Center records a second informational activity entry. Drift activity entries store normalized event metadata, such as expected template and revision, device id, detected timestamp, schedule drift reason when known, and affected outlet or role summaries when the comparison can produce them cleanly. They do not store raw expected or firmware schedule payload snapshots; current raw retained payloads and full generated schedule diffs belong in diagnostics. First ship does not persist historical raw MQTT payload snapshots for schedule drift events. Repeated retained-state messages for the same drift state do not create duplicate activity entries.

Schedule drift reasons are inferred best-effort from retained firmware state and recent mirror transitions. The first shippable reason set is deliberately small: `firmware_schedule_cleared`, `outlet_assignment_changed`, `schedule_body_changed`, and `unknown_firmware_change`. Command Center uses `firmware_schedule_cleared` when the retained active schedule body becomes empty or cleared, `outlet_assignment_changed` when a recent firmware-owned outlet assignment change explains removed or changed active schedule entries, `schedule_body_changed` when the active schedule body changed but no more specific clean reason is known, and `unknown_firmware_change` when Command Center lacks enough prior state or context to infer the cause. The current device drift state stores the current schedule drift reason for present-tense device-page copy and remediation prompts. If a device is already drifted with `unknown_firmware_change` and later retained state lets Command Center infer a more specific reason cleanly, Command Center may refine only the current device drift reason. Recent activity stores the reason snapshot for the drift-detected and drift-reconciled timeline entries, so refinement does not rewrite the original drift-detected activity entry or create another drift-detected event. Command Center does not parse firmware display text or treat the reason as definitive audit evidence.

The normal device-page schedule drift banner is summary-only. It shows the schedule drift reason, the expected source template and revision when known, and the canonical reconciliation actions Reload expected schedule, Save as new template, and Acknowledge drift. The server provides typed availability for these drift recovery actions, and the browser renders the returned visible, enabled, and disabled-reason states rather than duplicating the rules. Pending device actions do not disable the read-only `View details` action, but they do disable `Reload expected schedule`, `Save as new template`, and `Acknowledge drift` because those actions publish to firmware or mutate Command Center's template/expectation state while retained firmware state may still be in flux. It does not inline the full schedule diff or raw payloads. Reloading the expected schedule is a normal schedule load that publishes to firmware, so the action remains visible in the drift banner but requires firmware presence, retained `outlets/state`, retained `schedule/state`, and the stored expected active schedule. If the device is offline, Command Center disables reload with a device-offline reason; if retained preflight state is missing or still syncing, it disables reload with `Syncing retained state`; if the expected active schedule is missing, it disables reload with a missing-expected-schedule reason. The explicit `View details` panel fetches details on demand and shows a human-readable schedule diff first, using operator language for role, outlet, and schedule-entry changes. Command Center generates this human-readable diff when the details endpoint is called, from the stored expected active schedule and the latest mirrored firmware active schedule; it does not include the rendered diff in the normal device detail payload and does not persist rendered diff text. The details response may include compact diagnostic metadata needed to explain the diff, such as compared schedule fingerprints, expected template and revision ids, firmware schedule source, retained-state timestamps, or reason codes, but it does not return raw CE JSON or full payload-level diffs. `View details` is read-only and does not require the device to be online if Command Center already has current retained `schedule/state` and the stored expected active schedule. If retained `schedule/state` is missing or still syncing, Command Center may show the persisted drift banner but disables `View details` with a `Syncing retained state` reason until the latest retained schedule state is available. If the expected active schedule needed for comparison is missing, Command Center disables `View details` with a missing-expected-schedule reason. That diff compares the firmware-owned active schedule against the device's last confirmed expected active schedule, not against the current latest reusable template revision. The default diff view shows changed, removed, and added schedule entries, plus a compact unchanged-entry count when useful; unchanged entries stay behind an expand/details control. Removed entries that can be tied cleanly to an outlet assignment change use cause-specific copy explaining that the outlet assignment changed and CE firmware cleared affected schedule entries. Removed entries without a clean assignment-change explanation use generic removed-entry copy rather than guessing. If the source template has advanced, Command Center shows that separately as template update availability. Raw CE JSON and payload-level diffs remain in the minimal authenticated read-only diagnostics/developer detail path so the main device page stays readable and the details panel does not become a payload inspector.

Acknowledging schedule drift unlinks the device from the current expected active schedule while preserving prior load history. It is a local Command Center reconciliation action that does not publish MQTT, so it does not require the device to be online if Command Center already has current retained `schedule/state`. It requires current retained `schedule/state`; if retained schedule state is missing or still syncing, Command Center keeps the acknowledgement action visible but disabled with a `Syncing retained state` reason. It does not mutate the source schedule template, delete the historical load record, or claim the drifted firmware state is now a reusable template. After acknowledgement, Command Center shows the device as running firmware-owned state that is not currently linked to a schedule template.

Saving drifted firmware state as a schedule template is the separate explicit `Save as new template` action. The first shippable Command Center supports it for an eligible non-empty firmware active schedule, but does not support updating an existing reusable template from drifted device state. `Save as new template` is a local Command Center action that reads firmware-owned state and does not publish MQTT, so it does not require the device to be online if Command Center already has current retained `schedule/state`. If retained `schedule/state` is missing or still syncing, Command Center keeps the action visible but disabled with a `Syncing retained state` reason because saving depends on the current firmware-owned active schedule. If the active firmware schedule is empty or otherwise ineligible, Command Center disables it with a not-adoptable reason; if Command Center cannot convert the retained firmware schedule shape into a reusable template, it disables it with an unsupported-firmware-schedule reason. Updating an existing template is deferred because a reusable template may apply to multiple devices.

After `Save as new template`, Command Center automatically links the originating device to the new template and clears schedule drift only if the firmware active schedule used for adoption is still current at save time. The adopted firmware schedule becomes the device's expected active schedule for the new template revision. If retained firmware state changes during adoption, Command Center requires a refresh or retry instead of linking stale state.

Water Pump `Run Now` is exposed by Command Center as a device action against the active device schedule, not as schedule-template content and not as direct relay control. Command Center sends the firmware schedule-owned action for the selected Water Pump outlet and confirms the result from firmware-published schedule state or schedule errors.

Direct outlet on/off controls are exposed only as manual-mode device controls and are first-class pending device actions, not generic MQTT shortcuts. In AUTO, Command Center disables direct outlet toggles because CE firmware rejects direct relay writes while automation is active; the user must explicitly switch to MANUAL before direct outlet controls are available. Manual relay controls do not change the firmware active schedule body, the expected active schedule, template deployment state, or schedule drift; they are runtime relay activity shown through manual mode, mirrored relay state, and device action history. Command Center exposes explicit mode actions for switching to MANUAL, returning to AUTO, and performing an all-off manual stop. Switching back to AUTO requires clear user intent because CE firmware immediately evaluates the active schedule and turns unscheduled outlets off. After emergency all-off, recovery is a `Return to AUTO` action, not an automatic schedule reload. If the firmware active schedule body still matches the expected active schedule, returning to AUTO resumes it; if schedule drift exists, Return to AUTO is still allowed but the user must explicitly Reload expected schedule, Save as new template, or Acknowledge drift before expecting the device to match a template again.

Firmware time and sensor warnings are treated as device health warnings, not schedule-template validity errors. Command Center can edit templates from mirrored state and can load schedules when outlet preflight passes, but retained firmware schedule warnings such as missing valid wall time, unhealthy SNTP sync, or unavailable sensor data require explicit confirmation before loading or returning to AUTO. Command Center branches on firmware warning code and severity rather than parsing firmware display text. Remediable warnings should offer their remediation action before the user chooses to continue anyway.

Command Center uses the CE firmware MQTT time sync action rather than depending on the firmware web UI's browser-sync endpoint. Time source, timezone, and SNTP server settings remain configuration concerns, while setting the current wall time is a device action that firmware acknowledges by publishing retained schedule state with updated time health. Command Center confirms success from a newer `schedule/state` with source `time` and valid wall time, without requiring unrelated SNTP-health warnings to clear; it handles rejected actions from a newer matching `time/error` and keeps the wall-time recovery workflow inside the same MQTT integration boundary used for schedules, device actions, and mirrored runtime state.
