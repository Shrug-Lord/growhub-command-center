# Assignment-based schedule templates

Command Center schedule templates are assignment-based and portable, while CE firmware active schedules remain physical-outlet-based. Template entries use stable internal template role IDs plus editable assignments and user-facing outlet labels, so duplicate assignments such as two Fans or two Water Pumps can be mapped intentionally without breaking rules when a label is renamed. When loading a template, Command Center reads the target device's firmware-owned outlet state, preflights that every required template role can be mapped, and compiles the template into a complete CE v3 schedule payload for that device. Template loading is a full active-schedule replacement, not a merge with existing firmware schedule entries. If a user resolves a duplicate or label mismatch, Command Center persists the role mapping for that template/device pair using the stable role ID and physical outlet ID. A mapping remains valid across firmware label changes while the outlet assignment stays compatible; label drift is warning-only and does not block loading. Assignment changes or missing outlets invalidate the mapping. Extra assigned firmware outlets are allowed but receive no schedule entry from the compiled template, so Command Center must warn that they will not be automated and may turn off when the device enters AUTO. This lets one template apply across different physical outlet layouts, at the cost of requiring a compile/preflight step and explicit handling for duplicate, missing, renamed, or unused outlets.

Schedule templates have a lightweight revision that changes on each saved template edit. The revision is recorded with each device load so Command Center can show which template state produced an expected active schedule, without introducing full template version history as a shipping requirement.

The shippable schema cuts over to template roles and CE v3 outlet-condition schedules. Because Command Center has not shipped and current data is bench-only, the legacy `settings.sockets` schema and CE v2 relay-slot compiler are not preserved as a compatibility path. Development data may be reset or manually recreated during the cutover because the old model encodes physical slots, duplicates outlet assignment state, and produces a firmware schedule version that no longer matches the CE contract.

Template role conditions are stored in CE v3 condition vocabulary, attached to template role IDs instead of physical outlet IDs. The schedule editor may present friendly controls and display units, but persisted template data stays close to the firmware contract; compiling a template for a device primarily replaces template role IDs with firmware physical outlet IDs after assignment preflight.

Temperature thresholds are persisted in Celsius using CE v3 fields such as `low_c` and `high_c`. The user may choose Fahrenheit or Celsius for display and editing, but unit conversion happens at the UI boundary so stored templates remain independent of the user's current display preference and aligned with firmware validation.

Command Center may save draft schedule templates with incomplete template roles or missing conditions. Loading remains blocked until the template is load-ready: every required template role has at least one CE-valid condition, every required role can be mapped to the target device, and the compiled CE v3 payload contains at least one scheduled outlet.

Intentionally unused equipment is represented by omitting the template role. An empty role means the schedule template is a draft or incomplete, not that the equipment is intentionally unused. When the target device has assigned outlets that are omitted from the template, Command Center warns that those outlets will not be automated by the compiled schedule and may turn off in AUTO.

Command Center filters mapping candidates by the role's stable assignment. If exactly one physical outlet has that assignment, Command Center auto-maps it even when its firmware label differs from the template-role label, and reports the difference as non-blocking label drift. If several physical outlets share the assignment, one unique exact label match may break the tie and be inferred for preflight; otherwise the role mapping is ambiguous and the user must choose the physical outlet. Missing, duplicated, or non-matching labels never make an otherwise unique assignment match ambiguous. The chosen or inferred mapping is persisted for that template/device pair only after the schedule load confirms.

One physical outlet can satisfy at most one template role during a schedule load. When a template needs several rules for the same equipment, those rules are represented as multiple CE v3 conditions on one template role rather than separate roles mapped to the same outlet. Multiple roles mapped to one physical outlet are a role mapping conflict and block loading until the template or mapping is corrected.

Template role IDs are opaque immutable IDs generated when a role is created. They are not derived from assignment, label, order, or outlet type. Renaming, reordering, or changing role display data does not change the role ID. Deleting a role deletes its persisted mappings, and duplicating a template creates new role IDs so mappings from the original template do not attach to the copy.

Every template role has a required user-facing label. Command Center defaults the label from the assignment and auto-numbers duplicate assignments, such as `Fan 1` and `Fan 2`, while allowing the user to rename the label. If the user clears a label, Command Center stores a generated fallback instead of an empty label. Role labels are for human readability, duplicate-role mapping, and warnings; firmware validation remains based on the role assignment.

Template role labels are copied into the reusable template as a snapshot and are not live-linked to firmware outlet labels. If a firmware outlet label changes after a template has been mapped, Command Center shows label drift for that device mapping but does not rewrite the template unless the user explicitly updates the template label, saves a new template, or remaps the role.

Template load preflight reports label drift as a warning when a saved role mapping still points to a firmware outlet with a compatible assignment but the current firmware outlet label differs from Command Center's expected mapped outlet label. The saved mapping remains valid and the load can proceed. Assignment mismatches, missing outlets, ambiguous mappings, and role mapping conflicts remain load-blocking.

If label drift is shown during preflight, Command Center may offer outlet label repair as a separate explicit action. The user can choose to rename the firmware-owned outlet label to match the template's expected label, wait for retained outlet state confirmation, and then rerun preflight. The schedule load action itself does not rename firmware outlet labels.

Outlet label repair cannot run concurrently with schedule loading or another outlet configuration write for the same device. While label repair is pending, Command Center blocks schedule load actions until retained outlet state confirms or rejects the repair and preflight can be rerun against current firmware-owned outlet state.

The first shippable Command Center supports schedule adoption only as `Save as new template`. To adopt a drifted firmware active schedule, Command Center reverse-maps the firmware physical-outlet schedule through current retained `outlets/state`, creates new template roles from each scheduled outlet's assignment and label snapshot, and copies CE v3 conditions onto those roles. It does not update an existing reusable template from drifted device state in the first pass.

Only adoptable active schedules can be saved as new templates. Adoption requires current retained `schedule/state` with a non-empty CE v3 schedule, current retained `outlets/state`, and every scheduled physical outlet must exist in outlet state with a firmware-owned assignment other than `None`. Command Center snapshots labels from `outlets/state` and surfaces device health warnings, but time and sensor warnings do not block adoption. Adoption is blocked if the schedule is empty, unsupported, references an outlet missing from outlet state, references an outlet assigned `None`, or changes between preview and save.

Schedule adoption creates template roles only for physical outlets that appear in the adopted active schedule body. Firmware outlets that are assigned but unscheduled are omitted from the new template and may be shown as not adopted. This preserves the rule that intentionally unused equipment is represented by omitting the template role and avoids creating empty roles that would make the adopted template a draft immediately.

During adoption, Command Center snapshots firmware outlet labels but disambiguates adopted template role labels only when needed. If two scheduled outlets would produce duplicate role labels for the same assignment, Command Center appends a clear suffix such as `Fan - Outlet 2` and `Fan - Outlet 3` so the adopted template is understandable and loadable without requiring a firmware label change first. Distinct firmware labels are preserved as-is.

Disambiguating adopted template role labels does not create immediate label drift on the originating device. For the originating role mapping, Command Center keeps the adopted firmware outlet label as the expected mapped outlet label and compares future firmware label changes against that original snapshot. This lets adoption clear schedule drift without immediately replacing it with label drift caused only by template-label disambiguation.

When schedule adoption succeeds, the newly created template is immediately linked to the originating device and the adopted firmware schedule becomes that device's expected active schedule. If the retained firmware schedule or outlet state changed during adoption, Command Center does not create the link until the user refreshes and retries from current firmware state.
