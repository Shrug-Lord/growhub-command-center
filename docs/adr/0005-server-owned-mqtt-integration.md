# Server-owned MQTT integration

The Command Center server is the only MQTT client in the application boundary. The browser UI uses typed server APIs, and live browser updates can be added later through server-owned HTTP streaming or WebSocket delivery. This keeps broker topology and publish permissions out of the browser, gives Command Center one place to persist retained firmware state, and replaces generic topic publishing with purpose-built device actions.

Command Center migrates the existing React/Vite frontend, Express server, SQLite database, and MQTT integration in place instead of introducing a new stack for the CE firmware alignment. The server is a local companion service that should run on Windows, macOS, and Linux through Docker Compose, with advanced native deployment possible where Node.js, SQLite, process management, and an MQTT broker are available. ARM64 and AMD64 are both supported container targets, not hardware requirements imposed on an operator. Raspberry Pi is a supported reference deployment target, not a product requirement; implementation and documentation should avoid Pi-only assumptions where a generic local host works.

Docker Compose is the primary supported first-ship deployment path across Raspberry Pi, mini PC, and laptop hosts. The Compose deployment packages the Command Center server, SQLite app-data volume, MQTT broker, port publishing, restart policy, and reset/update commands into one documented workflow. Native Node, systemd, or other manual process-manager deployments may be documented as advanced paths, but they are not the first-ship happy path and should not drive the main install instructions.

Each first-ship Command Center installation runs exactly one application API process. Node cluster mode, multiple server containers sharing one app-data volume, and horizontally replicated API instances are unsupported because process-local rate limits, the server-owned MQTT client, retained-state mirroring, pending-action confirmation, and SQLite writes require one application authority. A reverse proxy may front that process for port publishing or TLS, and the MQTT broker remains a separate service; neither duplicates the application process. Command Center enforces this boundary by acquiring a cross-platform OS-backed exclusive file lock for its app-data directory before opening SQLite, connecting to MQTT, or starting the HTTP listener, and holds that lock for the process lifetime. Startup fails with a clear already-running or app-data-in-use error when another live process owns the lock. Kernel-managed ownership releases automatically on normal exit or process termination, including a crash, so restart recovery does not rely on PID checks, heartbeat timestamps, arbitrary stale intervals, or manual lock-file deletion. First ship supports app data only on a local filesystem, including a host-local Docker named volume or bind mount; network-shared filesystems and volumes shared across hosts are unsupported. Multi-process deployment is deferred until a demonstrated scaling need justifies shared rate-limit state, coordinated MQTT ownership, and a database designed for concurrent application replicas.

On `SIGTERM` or `SIGINT`, Command Center enters a bounded graceful-shutdown state before releasing application ownership. It first marks readiness false, stops accepting new HTTP connections, and rejects new MQTT-backed or other state-changing actions while allowing requests already in flight up to 10 seconds to drain. The MQTT connection remains available during that drain so already-published pending actions can still receive and persist retained confirmations. At the 10-second drain deadline, the server closes remaining HTTP connections and continues shutdown by disconnecting MQTT cleanly, checkpointing and closing SQLite, and releasing the app-data lock last. A hard 30-second total application deadline measured from signal receipt forces process exit if any subsystem still has not closed; OS ownership then releases the lock. The reference Compose deployment uses a 45-second stop grace period so normal cleanup or the application's own forced exit occurs before Docker sends an unconditional kill. These durations are fixed first-ship deployment defaults but are injectable through internal test configuration so automated shutdown tests do not wait on wall-clock production intervals.

First ship replaces the existing always-successful `GET /health` route with two unauthenticated minimal deployment checks. `GET /health/live` returns HTTP `200` with `{ "status": "live" }` while the HTTP process can respond. `GET /health/ready` returns HTTP `200` with `{ "status": "ready", "setup_required": true|false }` only after the app-data lock, deployment configuration validation, known SQLite migrations, and SQLite initialization have succeeded. Once graceful shutdown begins, readiness returns HTTP `503` with `{ "status": "not_ready", "reason": "server_shutting_down" }` for any request that reaches the existing listener. MQTT connection or subscription state does not affect application readiness because broker outages retain useful read-only application behavior and are represented separately in authenticated server health. Neither unauthenticated health response exposes broker state, devices, schedules, timestamps, errors, or other diagnostics, and first ship keeps no compatibility route at `/health` because the project has not shipped.

After graceful shutdown begins, middleware ahead of authentication and application routing returns HTTP `503 Service Unavailable` with stable reason `server_shutting_down` for every new API request observed on an existing connection, whether read-only, state-changing, setup, or authentication. Only `GET /health/live` and `GET /health/ready` bypass that middleware and retain their defined shutdown responses. A shutdown rejection does not create device action history, auth/security history, or persisted diagnostics records. The process emits bounded operational shutdown logging rather than one persistent or per-request event for every rejected request. The browser treats `server_shutting_down` as a temporary restart condition: it may retry normal reads after reconnecting to a ready server, but it never automatically replays a state-changing request because the original request may have crossed a persistence or MQTT boundary before the response was lost.

When the browser receives typed reason `server_shutting_down`, the authenticated app shell enters a confirmed restart-recovery state and shows `Command Center restarting`. A network failure, request timeout, or untyped proxy/gateway error instead enters an unavailable-recovery state and shows `Command Center unavailable`; the browser does not claim that the server is restarting without the typed shutdown evidence. Both states use a persistent, non-modal global banner, keep the last successfully rendered page visible as stale read-only data, disable all actions, and probe `GET /health/ready` with backoff beginning at one second and capped at five seconds without automatically reloading the page. If a confirmed restart has not reached readiness within 60 seconds, it escalates to `Command Center unavailable`; automatic readiness polling continues every five seconds while the page remains open. The unavailable state exposes `Retry now`, which triggers an immediate readiness probe without restoring controls, and a troubleshooting link. An outage that begins without typed restart evidence exposes those recovery actions immediately. After readiness returns, the browser revalidates the session and refetches authenticated server health plus the active page's current data. It clears the banner and restores actions only after those refreshes succeed. If session revalidation reports an expired or revoked session, the browser routes to sign-in normally. Recovery may retry idempotent reads, but it never automatically replays a state-changing request. A broker-only outage does not enter either server-recovery state while HTTP remains reachable; it keeps the separate broker-unavailable banner and its narrower MQTT-backed action restrictions.

The unavailable banner's troubleshooting link opens a panel whose content is bundled into the browser application and requires no new server request. It starts with platform-neutral checks such as confirming that the Command Center host and local network are reachable. For the primary deployment path, it tells the operator to open a terminal in the directory containing the Command Center Compose file and presents these copyable commands in order: `docker compose ps`, `docker compose logs --tail=200 server`, and `docker compose logs --tail=200 mosquitto` as inspection steps, followed by `docker compose up -d` and `docker compose restart server` as clearly labeled explicit recovery actions. It also links to the advanced native-deployment troubleshooting documentation for operators using that unsupported-as-default path. The panel must remain useful without internet access or a working Command Center API. It does not include destructive commands such as `docker compose down -v`, volume removal, database reset, restore, or Docker prune; those remain in their dedicated documented workflows with appropriate warnings. First ship does not expose an in-browser server restart control, remote shell, or generic host-command endpoint; host service recovery remains an explicit operator action outside the unavailable application.

The Command Center server emits operational logs to stdout or stderr as one structured JSON object per line with timestamp, severity level, component, stable event name, and only the redacted context needed to troubleshoot that event. It never logs passwords, raw credentials, MQTT URL user information, session identifiers, CSRF values, authentication payloads, raw request headers, raw MQTT payloads, or secret configuration. A device MAC address and typed MQTT topic may appear when needed to correlate local device behavior, matching the accepted diagnostics identifier boundary. Routine sensor messages and their values are not logged at normal levels; sensor-message metadata may appear only when debug logging is explicitly enabled and still may not include prohibited raw payloads or secrets. The advanced deployment setting `LOG_LEVEL` controls the server threshold, defaults to `info`, and accepts only the closed lowercase values `error`, `warn`, `info`, and `debug`. Command Center validates it before starting the HTTP listener and refuses startup with a clear configuration error for any other value. Changing the level requires a server restart. It is not editable in the Command Center UI; authenticated diagnostics may display the active level but cannot change it. Mosquitto may retain its native service log format. The reference Compose deployment configures Docker log rotation for both `server` and `mosquitto` with three files of at most 10 MB each per service, preventing troubleshooting logs from growing without bound.

Command Center generates a new opaque server-owned `request_id` for every HTTP request before normal middleware and routing using Node's built-in `crypto.randomUUID()`. The externally visible format is the canonical lowercase UUID v4 string. This applies to application, health, static-asset, and error responses whenever the server can construct a response. Command Center ignores any client-supplied request ID in first ship, returns the generated value in the `X-Request-ID` response header, and includes the same value unchanged in structured log records related to that request. The identifier contains no encoded user, device, address, or timestamp data. When a state-changing request creates a pending device action, the action stores its originating `request_id`; MQTT publication and later confirmation, rejection, interruption, or timeout logs include both `request_id` and `action_id`. The opaque request ID may appear in authenticated diagnostics and redacted diagnostics exports because it carries no secret or identity content. Requests that do not create a persisted action are correlated only through bounded operational logs and are not added to a general request-history table.

Normal UI surfaces show a request ID only for an unexpected HTTP `5xx` failure. The primary error remains concise and user-facing; an expandable error-details section labels the value `Reference ID` and provides a copy control. Expected validation, authentication, rate-limit, device-action conflict, `broker_unavailable`, and `server_shutting_down` responses do not display the request ID in routine UI because their typed reason and remediation are already actionable. Their `X-Request-ID` header and any authenticated diagnostic record still preserve correlation. This display rule does not change which responses receive an ID or which device actions persist one.

Every typed API error uses one JSON envelope: `{ "error": { "code": "...", "message": "...", "details": {} }, "request_id": "..." }`. `error.code` is a stable machine-readable reason, `error.message` is concise safe display text, and optional `error.details` contains only allowlisted structured context required by that error, such as field validation records, preflight blockers, `blocked_action`, or `blocking_action`. `request_id` duplicates the response header intentionally so browser and diagnostic clients can correlate errors without header-specific plumbing. Unexpected failures use stable code `internal_error` and a generic message rather than exposing implementation detail. No error body may contain a stack trace, raw exception, SQL, secret, credential, raw request data, or raw firmware/MQTT payload. The unauthenticated liveness and readiness endpoints retain their separate minimal response contract rather than using the API error envelope.

Successful typed API responses do not use a universal `{ "data": ... }` envelope. Each endpoint returns a direct object with stable descriptive top-level fields appropriate to its contract, such as `{ "device": ... }`, `{ "devices": [...] }`, `{ "action": ... }`, or `{ "preflight": ... }`. Endpoint-specific collection metadata such as pagination or summary values belongs beside the named collection when needed. Successful response bodies do not duplicate `request_id`; correlation remains in `X-Request-ID`. This avoids generic nesting while keeping each response extensible and explicit.

First ship includes a one-command update workflow for Docker Compose deployments, exposed as a documented script or make target. The happy path updates the app source or image, rebuilds images when needed, applies known SQLite migrations, restarts services, and preserves Docker volumes for SQLite app data and MQTT broker state. By default, the update workflow creates a backup before changing persistent state through migrations or service replacement. It may provide an explicit advanced `--skip-backup` or equivalent option, but the normal update path protects SQLite app data and MQTT broker state first. Manual git pull, build, and restart steps may remain documented for troubleshooting, but they are not the primary update path.

First ship also includes a one-command backup/export workflow for Docker Compose deployments before destructive reset or risky update work. The backup workflow creates a timestamped local archive containing the SQLite app-data volume and the MQTT broker persisted state needed for restore, and it handles SQLite safely enough for a consistent backup by stopping the service, using SQLite backup tooling, or otherwise preventing a live partial copy. Diagnostics bundle export remains separate because diagnostics is for troubleshooting current state, not restoring a deployment. Manual Docker volume backup instructions may remain documented for troubleshooting, but they are not the primary backup path.

First ship includes a documented one-command restore workflow from those backup archives. Restore is explicit and destructive: the operator must provide a backup archive path, the workflow stops services, replaces the SQLite app-data and MQTT broker persisted state, applies known migrations if the restored app database is older than the running version, restarts services, and prints a clear warning that current local state will be overwritten. Manual restore steps may remain documented for troubleshooting, but they are not the primary restore path.

Backup and restore ownership is limited to Command Center app data and the Compose-managed MQTT broker state. External MQTT brokers are an advanced deployment override, not the first-ship happy path. If an operator configures Command Center to connect to an external broker, the backup and restore workflows still handle Command Center app data but warn that external broker persistence is outside Command Center's backup scope and must be handled by that broker's own backup process.

Implementation starts with the server-side CE firmware mirror and action foundation before frontend workflow rewrites. The first implementation slice should establish retained MQTT mirroring, outlet/schedule/time contract handling, pending device action state, schedule-load preflight APIs, and diagnostics APIs so browser workflows can consume typed server state. Because Command Center is unshipped and bench-only, the first server schema work is a clean CE-aligned cutover rather than side-by-side legacy compatibility. Implementation may replace or drop legacy recipe/socket tables, columns, and semantics as needed, reset development data when appropriate, and model canonical CE concepts directly: device mirrors, retained topics, schedule templates and roles, expected active schedules, role mappings, pending actions, action history, and diagnostics. Legacy `settings.sockets`, grow-recipe, and `schedule_instances` behavior should not be preserved except as short-lived implementation scaffolding inside a single replacement diff.

The clean schema cutover uses an explicit operator or developer reset step instead of silently dropping incompatible tables on startup. Startup should fail with a readable legacy-schema or incompatible-schema message when old bench data is detected, and deployment documentation should provide easy reset instructions such as a dedicated database reset command or Docker volume reset path. This keeps the implementation free from legacy compatibility while avoiding surprise destructive behavior during bench deployment.

Command Center uses numbered SQLite migrations starting with the CE-aligned schema cutover, even though bench data can be reset before first ship. The initial migration may create the clean CE schema from scratch, and the reset command may drop and recreate the development database, but normal startup should apply known migrations and refuse unknown or incompatible schema state. This gives first ship a predictable upgrade mechanism without requiring compatibility code for obsolete bench-only data.

First ship treats the CE MQTT root topic `growhub/` as part of the firmware contract, not as a user-configurable topic prefix. Broker URL, credentials, and Command Center MQTT client ID are configurable deployment settings, but subscriptions and publishes use the fixed `growhub/<MAC>/...` topic shape. Supporting alternate topic roots is deferred until CE firmware has a real need for that contract change, because configurable prefixes would expand discovery, diagnostics, retained-state recovery, and action-confirmation test coverage.

MQTT broker connection settings are deployment configuration only for first ship, not editable through the Command Center UI. Operators configure broker URL, credentials, and client ID through documented environment variables or a local configuration file, and changing those settings is an operational restart or reconnect concern rather than an in-app device workflow. Advanced trusted-proxy support follows the same deployment boundary and is never configured through the first-run or settings UI. It is disabled when `TRUSTED_PROXIES` is unset or empty. When enabled, `TRUSTED_PROXIES` is a comma-separated allowlist of exact proxy IP addresses or CIDR ranges; only a request whose direct network peer matches that allowlist may supply a forwarded client address. First ship recognizes only `X-Forwarded-For`: for a trusted direct peer, Command Center parses the address chain from right to left, skips addresses covered by `TRUSTED_PROXIES`, and uses the first untrusted address as the client. It ignores `Forwarded` and `X-Real-IP`. If `X-Forwarded-For` is absent or malformed, or if the direct peer is not trusted, Command Center ignores forwarded-address headers and uses the direct peer. Command Center validates every `TRUSTED_PROXIES` entry before opening the HTTP listener and refuses startup with a clear configuration error if any entry is invalid, rather than silently weakening or partially applying the trust boundary. The first-run setup screen is intentionally admin-only and does not collect MQTT broker or trusted-proxy settings. Diagnostics may show broker connection status and redacted configuration shape, but it must not expose MQTT credentials. If Command Center is disconnected from the MQTT broker or has not completed its required subscriptions, the UI shows a global server or broker connection problem instead of escalating every device to `Device state not received`. The stable blocker and disabled-reason code for this condition is `broker_unavailable`; it is separate from `device_offline` and `retained_state_syncing`. Active broker outage state is exposed through global server health for normal UI banners, not duplicated as warning records in every normal device detail payload. The broker outage banner appears across the authenticated app shell when it affects core device workflows, including onboarding, device controls, schedule loading, Device setup edits, and diagnostics; it does not appear on login, first-run setup, or minimal deployment health-check surfaces. The banner is persistent but non-modal: navigation and read-only views remain usable from the last mirrored state, MQTT-backed controls are disabled inline with `broker_unavailable`, and the banner clears automatically when server health reports the broker connection and required subscriptions recovered. Banner copy stays concise, saying the broker connection is unavailable and MQTT-backed actions are paused, with a link to diagnostics rather than inline timestamps or last-error details. Device detail and action availability may still include `broker_unavailable` disabled reasons on affected controls so device pages can explain why MQTT-backed actions are unavailable. Broker outages and `broker_unavailable` endpoint responses are captured in global diagnostics/server health, not per-device action history. Per-device retained-state grace timers and retained-state incident creation are paused while the broker connection is unavailable, then restart from the reconnect time after Command Center is connected and subscribed again. This avoids presenting a server-side broker outage as proof that individual firmware devices failed to publish retained state. This also avoids building UI validation, secret redaction, reconnect rollback, and failure recovery before the CE alignment work is stable.

Authenticated on-screen diagnostics show whether trusted-proxy support is enabled and, when enabled, the exact validated IP/CIDR allowlist so an administrator can diagnose routing and trust mistakes. Ignored forwarded-address headers do not create persisted auth/security events and do not trigger a normal UI warning, because untrusted requests could otherwise flood bounded history and displace useful events. Instead, `global.trustedProxy` keeps a process-local aggregate with `forwarded_header_ignored_count`, `last_forwarded_header_ignored_at`, and `last_forwarded_header_ignore_reason`. First-ship reasons are `untrusted_peer` and `malformed_chain`. The aggregate retains no raw forwarded header or addresses and resets when the server restarts. Diagnostics bundle export does not include configured proxy addresses or ranges. Its redacted `global.trustedProxy` object contains `enabled`, `entry_count`, `exact_address_count`, `cidr_count`, and the same ignored-header aggregate fields; these values describe configuration shape and ignored-header activity without revealing local network topology.

The bundled Docker Compose MQTT broker remains anonymous and LAN-only for first ship because CE firmware does not currently support MQTT username/password auth. Command Center does not pause first ship to add credentialed MQTT support across firmware and deployment. In the reference Compose deployment, the broker is bundled with Command Center and should normally be available; `broker_unavailable` is expected only for infrastructure problems such as the Mosquitto service restarting, crashing, being misconfigured, failing health checks, or an operator choosing an alternate broker path. The broker is still a separate service rather than part of the Node process, so Command Center must keep the server-health and disabled-action handling. This is acceptable only with the documented LAN-only/no-internet-exposure deployment boundary, server-owned MQTT publishing, and no browser direct broker access. The first-ship Compose deployment should avoid exposing the Mosquitto WebSocket listener and port `9001`; live browser updates should use typed server APIs, polling, server-sent events, or server-owned WebSockets instead of browser MQTT.

First ship includes a simple authenticated device onboarding page for connecting CE firmware devices to Command Center. The page shows the broker host and port the firmware should use, explains that MQTT is configured in the CE firmware web UI, displays the fixed `growhub/<MAC>/...` topic shape, and shows the retained status topics Command Center is waiting for. The primary recommended broker host is derived from the browser's current host, such as `growhub.local` when the user visits `http://growhub.local`, with MQTT port `1883`. The page also shows detected LAN IP alternatives when the server can determine them, because mDNS or local DNS may not work on every network. The user does not have to configure the broker host during first-run setup unless the derived or detected values are wrong; an advanced override can live in settings or deployment configuration. When retained `growhub/<MAC>/status` arrives, onboarding marks the device as discovered or Connected and links it into the normal device list. Onboarding does not mark the device Ready until Command Center has mirrored retained `outlets/state` and `schedule/state`; until then it shows `Syncing retained state` or `Waiting for device state`. After the device is Ready, onboarding routes the user into Device setup to review firmware-owned outlet assignments and labels before setup is considered complete. Once Device setup review is current, onboarding is complete and the UI routes the user to the normal device page even if unrelated warnings still exist. Monitoring and read-only device views can work immediately, but onboarding must not imply the device is schedule-ready until outlet assignments and labels are reviewed or confirmed. Schedule loading remains gated by the existing preflight rules, and unresolved health or schedule warnings remain visible on the normal device page with their normal remediation actions. It does not auto-provision MQTT onto firmware for first ship because the device cannot receive MQTT commands until MQTT is already configured.

Device list and dashboard views show separate device summary signals instead of collapsing presence, setup review, retained-state sync, and health attention into one overall status. The UI can show signals such as Online or Offline, Setup needs review, Syncing retained state, and Needs attention at the same time because they lead to different user actions. Syncing retained state appears as a device summary signal only during startup or reconnect while required retained topics are missing; after the required retained state is mirrored, any narrower sync detail stays inline on affected controls or views. On Command Center server startup or MQTT broker reconnect, the 60-second grace timer starts proactively for each known device's required retained states after the server has a broker connection and required subscriptions are active; it is not started lazily by opening a page, viewing a device, or attempting an action. If the broker connection is unavailable, the UI shows a global broker or server connection problem and does not escalate per-device retained-state warnings until the connection and subscriptions recover. If required retained state remains missing for 60 seconds after startup or reconnect begins, the passive sync signal escalates to Needs attention with user-facing copy such as `Device state not received` and a link to troubleshooting or diagnostics. Normal UI copy describes the missing state in user-facing language, such as `Syncing outlet state` or `Syncing schedule state`, rather than exposing raw topic names like `outlets/state` or `schedule/state`; diagnostics can show logical retained keys and full MQTT topics. Needs attention is one aggregate signal on list and dashboard views, with a count and highest-priority summary when multiple warning conditions exist; individual warning records and remediation actions belong on the device detail page. On main surfaces that already show Setup needs review as its own signal, stale or blocked Device setup review does not also count inside Needs attention. On compact surfaces that only have one attention summary, the first priority order is pending or blocked action, schedule drift, invalid wall time, stale or blocked Device setup review, sensor unavailable, unscheduled assigned outlets, then lower-risk preflight or template warnings. This avoids treating outlet-label review, reconnecting firmware, syncing time, resolving schedule drift, and sensor warnings as one ambiguous device state, while also avoiding a noisy top-level signal for every warning type or showing the same setup issue twice.

Device setup review is stored against a normalized fingerprint of the current retained `outlets/state`. The fingerprint includes physical outlet id, assignment, and label, and ignores noisy fields such as firmware `source` and retained-message timestamps. If a later retained `outlets/state` changes any outlet assignment or label, Command Center clears Device setup reviewed and shows Device setup needs review again. Monitoring and read-only device views continue, but schedule loading is blocked until the user refreshes Device setup review against the current firmware-owned outlet state. Refreshing review requires an explicit `Confirm current setup` action in Device setup; opening the page does not count as review. If the user changes assignments or labels, the normal outlet config action runs first, and review is refreshed only after retained `outlets/state` confirms the exact intended full outlet config as the new firmware-owned state. A confirmed Device setup Apply marks that confirmed outlet-state fingerprint as reviewed, so the user does not need to click `Confirm current setup` again. If the outlet config action is rejected, times out, or retained outlet state no longer matches the intended full config, Command Center does not mark Device setup reviewed. If no changes are needed, `Confirm current setup` stores the current outlet-state fingerprint as reviewed. A successful `Confirm current setup` writes a local completed device action history entry with normalized metadata such as reviewed timestamp, outlet-state fingerprint, and whether the action refreshed a stale review. It does not create a pending action, publish MQTT, mutate firmware state, or persist raw retained payload snapshots. Device setup may show the last known outlet assignments and labels read-only while the device is offline or retained outlet state is syncing, but assignment and label edits are disabled until the device has current firmware presence and retained `outlets/state`. If retained `outlets/state` changes while a Device setup edit form is open, Command Center keeps the stale draft visible for reference, disables Apply, and shows an `Outlet state changed` conflict. The user may reload firmware state and discard the draft, or copy draft changes into a fresh draft based on the latest retained outlet-state fingerprint. Copying changes starts from the latest firmware-owned outlet state, carries forward only non-conflicting edits by physical outlet ID, and flags a per-outlet conflict when firmware changed the same outlet's assignment or label since the stale draft began. Apply remains disabled until all copied-draft conflicts are explicitly resolved. The confirmation action is disabled while retained outlet state is missing or syncing, while an outlet config action is pending, or while the current outlet state has an outlet label conflict. The setup confirmation disabled reason for a label conflict is the stable code `outlet_label_conflict`. Intentionally unassigned outlets do not disable confirmation. Device health warnings, schedule drift, unscheduled assigned outlets, sensor warnings, invalid wall time, and template preflight warnings remain visible in their own workflows, but they do not block `Confirm current setup` unless they directly affect outlet assignment or label ambiguity.

First ship requires a single admin login for the Command Center UI and typed API instead of allowing unauthenticated local-network access. Admin credentials are created through a first-run setup screen in the UI, not through environment variables, local config files, or shipped default credentials. Setup collects a local admin username and password; the username defaults to `admin`, login uses username plus password, and first ship does not collect email because there is no cloud account, email recovery, or multi-user account model. Username input is trimmed, normalized to lowercase for storage and display, and validated as 3-32 characters containing only letters, numbers, `.`, `_`, and `-`; whitespace and `@` are rejected. Login is case-insensitive because submitted usernames are normalized before comparison. Admin passwords must be 12-128 characters, must be entered with confirmation during first-run setup, may include spaces and symbols, and must not be all whitespace. First ship does not require password composition rules such as uppercase, number, or symbol requirements. Until setup is complete, unauthenticated access is limited to the setup flow and minimal health checks needed for deployment troubleshooting; after setup, unauthenticated access is limited to login and those health checks. The first-ship auth API is session-oriented: `POST /api/v1/setup` creates the admin during first-run setup, `POST /api/v1/session` logs in with username and password and creates a session, `GET /api/v1/session` returns the current session plus CSRF token, and `DELETE /api/v1/session` logs out by revoking the current session. The legacy `POST /api/v1/auth` login shape is not kept for first ship because Command Center has not shipped and does not need compatibility for old clients. Once setup is complete, the first-run setup endpoint is permanently closed unless local app data is intentionally reset; later unauthenticated setup attempts return a typed conflict such as HTTP `409` with `setup_complete` and must not replace the admin login. Unauthenticated minimal health checks prove only that the Command Center HTTP process is reachable and may expose a minimal setup-routing field such as `setup_required: true|false`; they do not expose MQTT broker status, subscription readiness, broker timestamps, retained-state rebuild status, device counts, device identifiers, schedule state, or broker errors. Login, first-run setup, and minimal health-check surfaces stay separate from the authenticated app shell and do not render the broker outage banner. First ship does not introduce multi-user accounts, roles, or per-feature permissions. Authenticated access is required for normal device pages, schedule and outlet workflows, MQTT-backed device actions, local reconciliation actions, server health, diagnostics, and diagnostics bundle export. This keeps setup easy for a local companion server while protecting relay control, outlet assignment, schedule loading, broker topology, and raw diagnostic data from casual LAN access.

The first-run setup stores the admin username locally and stores the admin password only as a password hash in SQLite. Password hashes are self-describing: the stored verifier carries the hash algorithm/version and cost or parameter metadata needed to verify the password later, rather than relying on an implicit global setting or a fragile external migration. When a login succeeds and the stored hash verifies but uses an older supported algorithm or weaker parameters than the current implementation target, Command Center may transparently rehash the submitted password and replace the stored verifier. Failed logins do not rewrite password state. It also generates a persistent random session secret during setup. The session secret is stored in the local app data directory with restrictive filesystem permissions rather than shipped as a default value or required as deployment configuration. Command Center uses server-side SQLite session records rather than self-contained signed session cookies. The HTTP-only cookie contains only an opaque random session id, while SQLite stores only a hash of that session id plus server-owned metadata such as created time, last-seen time, expiration time, revocation state, and CSRF token hash. The browser never receives session contents, admin metadata, or authorization claims in the cookie. Resetting the app data can intentionally return Command Center to first-run setup and invalidates existing sessions by removing the persisted session secret and session state. Normal server or container restarts keep existing sessions valid. First ship uses a simple 30-day rolling session lifetime with no `remember me` option; authenticated activity may extend the session window, while idle sessions expire after the rolling lifetime.

Browser authentication uses an HTTP-only same-site session cookie rather than localStorage bearer tokens. The browser does not need direct session credential access, and keeping the session credential out of frontend JavaScript reduces exposure from script compromise. `POST /api/v1/session` returns a per-session CSRF token alongside the normal authenticated session response, and `GET /api/v1/session` can return a fresh/current CSRF token after page reload. The browser keeps the CSRF token in memory only, not `localStorage`, and sends it in an `X-CSRF-Token` header for authenticated state-changing typed API calls. The server validates the header against the CSRF token hash stored with the SQLite session record. Missing or invalid CSRF headers return HTTP `403 Forbidden` with typed reasons `csrf_required` or `csrf_invalid`; they do not automatically invalidate the session. On a CSRF failure, the browser may call `GET /api/v1/session` once to refresh its CSRF token and retry or let the user retry the intended action; if that refresh fails because the session is expired or revoked, the browser routes to sign-in. Read-only GET calls still require the authenticated session except for setup, login, and minimal health-check endpoints, but they do not require a CSRF token. `POST /api/v1/session` and `POST /api/v1/setup` establish the session boundary and are protected by same-origin deployment, generic errors, and rate limiting rather than requiring an existing CSRF token.

Production browser access is same-origin only for first ship: the built UI and typed API are served from the same scheme, host, and port, with API calls made under that origin. Cross-origin browser API access is not a production feature when cookie sessions are used. Local development may allow an explicit Vite dev origin such as `http://localhost:5173` through a development-only configuration flag, but production must not use wildcard CORS or credentialed CORS for arbitrary origins.

First ship supports plain HTTP for local LAN and self-hosted deployments. Command Center must not be exposed directly to the internet over plain HTTP; remote access should use a VPN or an HTTPS/TLS reverse proxy. Session cookies are always `HttpOnly` and `SameSite`, and the cookie `Secure` flag is enabled when Command Center is served over HTTPS. Built-in TLS is deferred because certificate setup would add deployment friction across Raspberry Pi, mini PC, laptop, and Docker deployments.

The reference Docker/local deployment binds Command Center for LAN access by default so phones, tablets, and laptops on the same trusted network can reach `http://growhub.local` without a port suffix when local DNS or mDNS is configured. The preferred reference deployment publishes host port 80 to the Command Center server, even if the Node process listens on an internal unprivileged port such as 3000. Users who cannot use host port 80, or who want proxy-only or localhost-only exposure, can set an explicit host port or bind override, such as binding Docker port publishing to `127.0.0.1`. This keeps the default aligned with the local appliance model while preserving narrower deployment options for users fronting Command Center with a reverse proxy.

Command Center treats `growhub.local` as a reference hostname target provided by host or network configuration, not as a service the Node app advertises itself. First ship does not bundle mDNS advertisement into the application server. Reference deployment documentation may instruct users to set the host name to `growhub`, configure local DNS or mDNS on the host OS, or use a different local hostname/IP when their OS or router setup differs.

First ship includes admin logout plus authenticated username and password change in the UI. Logout invalidates the current session. Username change requires the current admin password, applies the same trim/lowercase/character validation used during first-run setup, writes the new normalized local username, and invalidates all existing sessions so the admin signs in again with the new credential. Password change requires the current admin password, requires new-password confirmation, applies the same 12-128 character length rule, allows spaces and symbols, rejects all-whitespace passwords, avoids composition rules, writes a new password hash, and invalidates all existing sessions for the same reason. Admin replacement is not supported through the first-run setup endpoint after setup is complete. Forgotten-username or forgotten-password recovery is not an email, security-question, or multi-user workflow; the documented recovery path is to reset the local app data, which intentionally returns Command Center to first-run setup.

First ship includes basic process-local fixed-window rate limiting for first-run setup, login, username-change, and password-change endpoints. Each bucket stores `window_started_at` and `count`. Its first request anchors `window_started_at`; every later request within that fixed window increments `count`, including requests already being throttled, but never moves the anchor or extends the window. When the window expires, the next request starts a fresh window with `count` equal to one. `Retry-After` is derived from the fixed window end. All in-memory buckets reset on server restart. Sliding windows are deferred unless bench or production evidence shows that fixed-window boundary bursts are a meaningful problem. Every request reaching one of these endpoint boundaries counts before credential validation, not only failed authentication. The client-IP bucket is evaluated and incremented before body or credential validation, so malformed requests still count against the IP dimension. Login also increments its normalized-username bucket only when a username can be parsed and normalized. Username-change and password-change requests increment their authenticated-admin bucket only when a valid current auth context is available. If evaluating the client-IP bucket leaves the request throttled, an available normalized-username or authenticated-admin bucket is incremented only when that exact secondary bucket already exists; the request never allocates a new secondary identity bucket. Missing or malformed identity input therefore affects only the IP bucket, and neither successful authentication nor a successful setup or credential change resets any bucket; buckets expire only through their configured window. Login attempts use separate buckets for client IP and normalized submitted username, first-run setup uses a client-IP bucket because no session exists yet, and authenticated username-change and password-change attempts use client IP plus the current session or admin identity where available. Password protection relies on validation, rate limiting, and secure password hashing rather than composition rules. Unauthenticated login, setup, and session-check failures use generic user-facing errors. Stable typed machine reasons are allowed only where they are needed for routing or control flow, initially `setup_complete`, `rate_limited`, and `session_required`. Repeated failures return generic authentication errors and then typed `429` responses with `rate_limited` when throttled; responses should not reveal whether a username, password, session id, or setup state was the specific failure. Missing usernames, wrong passwords, expired sessions, revoked sessions, and unknown session ids collapse to generic authentication or `session_required` responses rather than distinct user-facing messages or distinct reason codes. Persistent or distributed rate limiting is deferred until the local appliance model shows evidence that it is needed. The first-ship limiter is intended to slow casual brute-force attempts and repeated credential-change attempts on the local network without introducing a full security audit or distributed abuse-prevention system.

The first-ship limits are: `setup_ip` allows 5 requests per 10 minutes; `login_ip` and `login_username` each allow 10 requests per 5 minutes; and `username_change_ip`, `username_change_admin`, `password_change_ip`, and `password_change_admin` each allow 5 requests per 15 minutes. The first request after an allowed count returns HTTP `429` with stable reason `rate_limited`. The response includes a standard `Retry-After` header expressed as whole seconds, rounded up to the time when every bucket tripped by that request permits another attempt. If multiple buckets are blocked, Command Center uses the longest remaining delay and does not identify which bucket produced it in the unauthenticated response.

Expired rate-limit buckets are deleted or replaced lazily whenever their key is accessed, and a process-local sweep every five minutes removes all other expired buckets. The process enforces a hard capacity of 10,000 active buckets. Before allocating a new bucket at capacity, Command Center runs an immediate expiry sweep. If capacity remains full, it does not evict an active bucket or allocate the new key; it rejects the request with HTTP `429` and stable reason `rate_limited`, with `Retry-After` rounded up to the earliest active bucket expiry. Capacity overflow does not create a per-bucket throttle event or normal UI warning. Bucket state and capacity-overflow aggregates reset on restart and are never persisted, normal bucket expiry does not create an auth/security event, and diagnostics never expose raw bucket keys. Authenticated diagnostics and diagnostics bundle export may expose only `global.rateLimiting.active_bucket_counts`, `bucket_capacity`, `bucket_overflow_count`, and `last_bucket_overflow_at`. Active counts are keyed by the closed stable bucket-category enum. These values reveal limiter activity and capacity pressure without exposing IP addresses, submitted usernames, session identifiers, admin identities, or internal bucket keys.

Auth/admin events are not device-scoped and do not enter device action history. First ship keeps only a bounded local auth/security event history for authenticated diagnostics. The initial normalized event types are setup completed, login succeeded, logout, username changed, password changed, sessions revoked, and rate-limit throttles. The history retains only events that are both within the latest 100 entries and no older than 30 days; older or excess records are pruned on write and at server startup. This bounded diagnostic history is not a full audit log. Each setup-completed, login-succeeded, logout, username-changed, password-changed, and rate-limit-throttle event retains the server-observed client IP address for LAN troubleshooting. Authenticated or successful events may also retain the normalized admin identity, but failed or throttled login events do not retain the submitted username or username-bucket value. Client IP means the direct network peer by default; Command Center honors forwarded client-address headers only when `TRUSTED_PROXIES` is valid and the request's direct peer matches its allowlist. Failed-login details are not shown in normal UI. Auth/security event records may include other metadata needed for diagnostics, such as server timestamp, event type, stable reason code, and rate-limit bucket category, but they must not store passwords, raw credentials, session ids, CSRF tokens, or raw submitted login payloads.

Rate-limit throttles are coalesced so one noisy client cannot consume the bounded history. A throttle event is keyed by server-observed client IP and stable rate-limit bucket category. The closed first-ship category enum is `setup_ip`, `login_ip`, `login_username`, `username_change_ip`, `username_change_admin`, `password_change_ip`, and `password_change_admin`. These categories identify the protected operation and limiter dimension without exposing an internal bucket key. If one request trips multiple limiter buckets, Command Center records or coalesces one throttle event for each tripped category. A matching throttle updates the existing event's `last_at` and increments `count`, while preserving its original `first_at`, only when both `now - last_at` is no more than five minutes and `now - first_at` is less than 24 hours; it remains one entry toward the 100-event limit. If either condition fails, the throttle creates a new event. Throttle-event recency ordering and 30-day age pruning use `last_at`, and pruning runs when a coalesced event is updated as well as when a new event is inserted. This limits a continuously noisy source to at most one event per category per 24-hour span without discarding evidence of recent activity. Coalescing never stores a normalized submitted username, username-bucket value, session id, admin bucket key, or raw login input.

The server auto-registers devices from valid CE MQTT retained topics under `growhub/<MAC>/...`; first ship does not require the user to manually enter a MAC before a device appears. Auto-registration creates a local device record keyed by firmware MAC, uses a generated display name until the user renames it, and does not publish MQTT or mutate firmware state by itself. Users can hide devices from normal views when stale retained broker topics or bench hardware should not be shown. A forgotten device may reappear if valid retained CE topics for that MAC still exist, because the broker is still advertising the device; hiding is the durable UI-level suppression.

The first Command Center release documents CE firmware `1.1.0C` as its tested compatibility baseline because that release introduces the retained outlet assignment/label and MQTT time-action contracts used here. Runtime workflow gating is capability-based rather than based only on lexical comparison of the firmware's display version: Command Center validates required retained topics, payload versions, fields, and enums before using them. A device that lacks a required contract remains visible for monitoring when possible, but dependent setup, scheduling, or action workflows stay blocked with a firmware-compatibility explanation after the normal retained-state grace period. Diagnostics identify the missing or unsupported contract, and release notes record the exact CE version bench-tested with each Command Center release. A newer reported firmware version is not rejected solely because it is newer when its public payload contracts validate.

The server persists a device mirror for each discovered device. The mirror stores the latest retained firmware outlet state, schedule state, presence, and recent firmware error state as raw JSON for fidelity, with indexed columns for list and filter concerns such as online state, last-seen time, firmware version, and current mode. The UI reads the device mirror instead of reconstructing current device state from sensor history or browser MQTT messages.

For the first shippable version, the browser refreshes device views through typed HTTP polling against the server mirror. The authenticated app shell consumes a separate global server-health payload for Command Center-wide conditions such as broker connection state, so authenticated pages can render one shared broker outage banner without relying on each device detail payload to carry that banner state. The server-health payload is authenticated and exposes one simple broker state for UI decisions, such as `connected`, `connecting`, or `unavailable`, and compact recovery detail for troubleshooting, including `subscriptions_ready`, `last_connected_at`, `last_disconnected_at`, and a redacted `last_error` or stable error code when present. It may also include retained-state rebuild summary counts, such as devices waiting for required retained state, without embedding per-device incident rows. The normal device detail payload includes drift recovery action availability derived from the current device mirror and persisted drift state, so the device page receives drift action state with the rest of its page state instead of calling a separate availability endpoint. The normal device detail payload does not include the human-readable drift diff; `View details` calls a read-only details endpoint that recomputes and returns the diff on demand. That endpoint returns human-readable drift detail plus compact diagnostic metadata needed to explain the comparison, not raw CE JSON or full payload-level diffs. Device actions trigger an immediate refetch, and normal polling catches later retained-state changes. Server-sent events or WebSockets can be added later if polling is not responsive enough, without changing the CE firmware MQTT contract.

The normal device detail payload also exposes aggregate typed current warning records derived from the device mirror, including retained-state conditions such as `Device state not received`. Retained-state warning records use one stable warning code, `device_state_not_received`, with an `affected_states` array such as `["outlet_state", "schedule_state"]` rather than separate warning codes per missing retained key. This warning is not user-dismissible and has no acknowledgement state; normal UI may link to troubleshooting or diagnostics, but it must not offer dismiss or acknowledge controls for the warning itself. A single closed retained-state category enum is shared across normal warnings, disabled action context, and preflight blockers; first-ship values are `presence_state`, `outlet_state`, and `schedule_state`. The `presence_state` category only means retained presence/status is missing during onboarding, startup, or reconnect recovery and is needed to rebuild the mirror; a known offline device remains a separate `device_offline` condition or signal. Those affected-state values are friendly state categories, not MQTT topic strings, so the UI can show actionable copy and disabled-action reasons without exposing raw MQTT topic names. Disabled action records that use `retained_state_syncing` also include the complete friendly category set they are waiting on, sorted in retained-state category enum order, such as `missing_states: ["schedule_state"]`, so each action can explain every specific missing input without exposing retained MQTT topics or incident rows. The normal device detail warning list does not include global server-health records such as active `broker_unavailable`; action availability can still cite `broker_unavailable` as the disabled reason for MQTT-backed actions. Full retained-state incident records, resolved incident history, and per-key troubleshooting metadata remain diagnostics-only.

Typed device-action HTTP endpoints return after the server successfully publishes the MQTT command, without blocking for firmware confirmation because the CE firmware contract does not include request IDs that would make direct command-response correlation reliable. A published action awaiting retained-state or firmware-error confirmation returns HTTP `202 Accepted` with direct body `{ "action": ... }` showing pending status and a `Location` header identifying that device-action resource. The browser reads or refreshes that resource until the action becomes completed, rejected, interrupted, or timed out. An immediate no-op or synchronously completed local action returns HTTP `200 OK` with `{ "action": ... }` showing its terminal result and does not pretend to be pending. Every valid submitted no-op is persisted as its own canonical completed action with `reason_code: "already_in_requested_state"`, identical `created_at`, `updated_at`, and `completed_at` operation timestamps, and `timeout_at: null`; it publishes no MQTT. Command Center resolves pending actions when the device mirror reflects the expected retained-state change or a relevant firmware error appears. When `broker_unavailable` is active, MQTT-backed device actions are visible but disabled, and final MQTT-backed action endpoint attempts are rejected before publish with HTTP `503 Service Unavailable` and a typed `broker_unavailable` response body. Those 503 responses do not create pending actions or per-device action history entries; diagnostics/server health records the broker outage. Read-only views continue to render from the last mirrored state while also showing the non-modal global broker connection warning.

MQTT-backed actions persist internal publish state before transport handoff so a process failure cannot erase an attempted command. The server first stores the action as prepared with public `timeout_at: null`, then records whether it was submitted to the MQTT client and acknowledged at the publish boundary. At MQTT handoff, the server persists internal `submitted_at` and sets the public absolute `timeout_at` to exactly 15 seconds after that instant because firmware may receive and execute the command immediately. Every first-ship MQTT-backed action uses this same 15-second firmware-confirmation deadline; synchronous local-only actions do not receive a confirmation deadline. After handoff, the HTTP endpoint waits at most three seconds for the QoS 1 publish callback/PUBACK, but never waits for firmware confirmation. That wait does not pause or extend the deadline, so a `202` response may show part of the confirmation window already elapsed. If PUBACK arrives in that window, the server records acknowledged publish state and returns `202` with the pending action. If the message was handed to MQTT but PUBACK has not arrived after three seconds, the server still returns `202` with the action pending because firmware may execute it. A later publish callback error changes that action to `interrupted` with `mqtt_publish_failed`, which normal action polling surfaces. A definite synchronous rejection before MQTT accepts the message marks the action `interrupted` with `reason_code: "mqtt_publish_failed"` and returns HTTP `502` with typed `action_publish_failed` plus the canonical terminal action in allowlisted error details. Retained state, a relevant firmware error, or the original deadline resolves any action that remains pending; PUBACK alone never marks the device action completed. On restart, a prepared action that was never submitted becomes `interrupted` with `server_restarted_before_publish`. A submitted but unconfirmed action remains pending under its original absolute deadline. Browser polling and process downtime never extend or replace that deadline. Command Center never automatically republishes an uncertain action because CE firmware may already have applied the first message. Internal publish state is diagnostic lifecycle metadata and does not add another public action `status`.

Each valid firmware state message advances a persisted monotonic mirror revision for that device and logical state stream, including a valid repeated payload. Before MQTT handoff, an action captures the current revision of every retained state stream used by its confirmation predicate. The action can complete only from a matching valid firmware state message whose observed revision is greater than the captured base revision. Merely rereading an unchanged current mirror row, replaying a previously processed retained message, or receiving no newer state cannot confirm it. If current state already satisfies the request before handoff, the request follows the completed no-op path instead. Base revisions are internal action lifecycle metadata and are not exposed in the canonical action resource. Persisting both mirror revisions and action base revisions allows submitted pending actions to retain the same confirmation rule across a Command Center restart.

Firmware rejection events use the same temporal guard. Command Center maintains a persisted monotonic observed sequence per device and logical firmware error stream, captures the relevant base sequence before handoff, and rejects a pending action only from a valid later error on the stream assigned to that action. CE `schedule/error` and `outlets/error` payloads do not contain a `command` field, so topic plus post-handoff sequence identifies those errors: `schedule/error` resolves the sole pending schedule-family action, covering schedule loads, expected-schedule reloads, or Pump Run Now, and `outlets/error` resolves the sole pending outlet configuration or label-repair action. `time/error` must additionally identify `time/action`, and `control/error` must identify the corresponding `control/mode` or `control/relay` command. Older errors, malformed errors, and errors on another stream or with a mismatched available command may update bounded diagnostics but never resolve the action. Command Center permits at most one pending consumer of each device error stream because CE errors do not include request ids. Error base sequences and raw firmware details remain internal; the terminal action stores only the normalized Command Center rejection reason.

A pending `sync_time` action completes only from a newer valid retained `schedule/state` revision that reports both `source: "time"` and `time_valid: true`. It does not require `time_warning` to be empty or the `warnings` array to contain no time-health warning: setting valid wall time can succeed while configured SNTP remains pending, stale, or otherwise unhealthy. Those current health warnings remain visible and independently remediable after the action completes. Command Center does not compare the requested epoch because CE does not echo it in retained state. A newer matching `time/error` rejects the action under the command-family error rule; otherwise the 15-second deadline applies.

Relay-mode actions confirm from mode alone in a newer valid retained `schedule/state` revision. `switch_to_manual` completes when `mode` is `manual`, and `return_to_auto` completes when `mode` is `auto`. Switch to MANUAL does not compare relay outputs with a pre-action snapshot because firmware preserves whatever outputs it currently has. Return to AUTO does not require any particular outlet-state pattern because firmware immediately evaluates the active schedule and may legitimately change several outputs. Command Center mirrors those runtime outputs normally, but they are not part of either mode action's confirmation predicate. A newer matching `control/error` for `control/mode` rejects the action; otherwise the 15-second deadline applies.

`emergency_all_off` has a compound confirmation predicate because it promises both manual takeover and de-energized outputs. It completes only from one newer valid retained `schedule/state` revision with `mode: "manual"`, exactly one valid `outlet_status` entry for each physical outlet id 1-4, and every entry reporting `state: "off"`. MANUAL mode without all four confirmed OFF states remains pending. If the current mirror already satisfies the complete predicate before handoff, the request records a completed no-op. A newer matching `control/error` for `control/mode` rejects it; otherwise the 15-second deadline applies. The urgent action may supersede other actions under the accepted conflict policy, but Command Center does not report its own success before firmware publishes the full safe state.

`set_manual_outlet_state` confirms the complete relay result, not only the outlet named by the operator. Before handoff, Command Center computes and stores the intended full four-outlet relay mask from current mirrored state. The action completes only from one newer valid retained `schedule/state` revision with `mode: "manual"`, exactly one valid `outlet_status` entry for each physical outlet id 1-4, and an outlet-state pattern exactly matching that intended mask. This verifies that the firmware's full-replacement `control/relay` command preserved every other outlet as intended. If current MANUAL state already matches the complete intended mask, the request records a completed no-op. A newer matching `control/error` for `control/relay` rejects it; otherwise the 15-second deadline applies. The intended full mask is internal confirmation metadata; public action context retains the target outlet id, outlet-label snapshot, and requested target state.

`run_water_pump_now` completes only from one newer valid retained `schedule/state` revision with `mode: "auto"` and the targeted physical outlet's structured `outlet_status.state` equal to `on`. Command Center never parses the firmware-owned `summary` display string for action logic. If the target pump is already ON in current AUTO state before handoff, the request records a completed no-op, matching CE's idempotent duplicate behavior without extending or restarting the run. A newer matching `schedule/error` rejects it; otherwise the 15-second deadline applies. Because CE does not publish a structured Run Now correlation field, Command Center confirms the achieved pump-running state rather than claiming which actor caused it.

Schedule loads, expected-schedule reloads, and Pump Run Now are serialized as one schedule-error family per device. While any one is pending, Command Center rejects the others, including Run Now for a different pump, because a commandless `schedule/error` could not be attributed safely and each action also observes retained `schedule/state`. Time sync, assignment-changing outlet config, and relay-mode changes also conflict with pending Pump Run Now because each can re-evaluate schedules, invalidate the pump schedule, or change the AUTO mode required by the action. Label-only outlet repair and read-only refresh remain allowed. A second pump may be started after the first action confirms, so this confirmation serialization does not prohibit multiple pumps from running simultaneously.

The canonical device-action resource is `GET /api/v1/devices/:deviceId/actions/:actionId`, and a pending response's `Location` header uses that URL. Command Center generates each canonical action id as a lowercase UUID v4 with `crypto.randomUUID()`. The identifier is globally unique and opaque, but action lookup remains device-scoped through the route. A nonexistent action id and an action id associated with a different device both return the same typed `404 action_not_found` response so the API does not disclose cross-device relationships. The canonical id remains unchanged for the action's entire pending and retained-history lifetime. Pending and terminal action responses use one stable representation containing `id`, `device_id`, `type`, `status`, `created_at`, `updated_at`, nullable `timeout_at`, nullable `completed_at`, nullable stable `reason_code`, and an allowlisted action-specific `context` object when needed. The closed first-ship status vocabulary is `pending`, `completed`, `rejected`, `timed_out`, `interrupted`, and `blocked`. `pending` means an accepted action is awaiting authoritative completion; `completed` covers firmware-confirmed actions and synchronous local completions; `rejected` means firmware explicitly rejected a published action; `timed_out` means its confirmation deadline expired; `interrupted` means Command Center can no longer complete or confirm it; and `blocked` means the server refused the action attempt before MQTT publication because another action or current device state prevented it. Every terminal status is immutable. Later retained firmware state always updates the authoritative current device mirror, but it never changes a terminal action's status, timestamps, reason, or attribution. In particular, state that appears to satisfy an action after its 15-second deadline does not convert `timed_out` to `completed`, because the CE contract has no request id proving that the late state resulted from that action. Command Center does not create a late-confirmation warning, action, or device event. Current-state warnings clear normally when the mirror becomes healthy, while Recent activity keeps the original timed-out action. Timeout UI copy says `Device confirmation was not received. Check the current device state before retrying.` It does not claim the firmware rejected or ignored the command. Ambiguous `failed` and `cancelled` statuses are excluded. Request validation failures that never create an action remain typed API errors and do not receive an action status. `reason_code` uses a closed Command Center-owned vocabulary rather than exposing firmware strings directly. Known stable firmware reasons map to prefixed codes such as `firmware_invalid_epoch`; Command Center-owned outcomes use codes such as `confirmation_timeout`, `conflicting_action`, and `device_state_changed`. `rejected`, `timed_out`, `interrupted`, and `blocked` actions require a reason code, while `pending` and ordinary `completed` actions use `null`; a completed no-op instead uses `already_in_requested_state`. An unrecognized firmware reason maps to `firmware_rejected`, with the raw reason retained only in authenticated diagnostics. UI copy is derived from the normalized code and never displays the code itself as operator-facing text. Each action type has a closed context schema containing only the small immutable display snapshot needed to explain what the user acted on. Schedule loads store `template_id`, `template_name`, and `template_revision`; manual outlet actions store `outlet_id`, `outlet_label`, and `target_state`; mode changes store `target_mode`; outlet configuration writes store the affected physical `outlet_ids`; and time sync omits context unless a later requirement justifies a typed field. Stable ids and display snapshots are captured when the action is created. Later template deletion or renaming and later outlet-label changes never rewrite historical action context. Context is not an arbitrary property map and never stores full schedules, full outlet configurations, raw MQTT payloads, or raw firmware responses. The normal action resource also excludes the originating `request_id`; those diagnostic details remain available only through authenticated diagnostics where applicable. While the pending-action feedback remains visible and the browser tab is active, the browser polls the action resource once per second. It pauses dedicated action polling when the tab is hidden or the user leaves that workflow, performs an immediate action and device refresh when they return, and stops dedicated polling after a terminal status. Normal device polling continues to surface pending or terminal action state elsewhere in the application. The browser does not establish its own action timeout or change action status based on missed polls; the persisted server deadline and server-side confirmation rules remain authoritative.

Every terminal action immediately releases its serialization lock. A user-initiated retry is always a new request with fresh authorization, validation, current-mirror preflight, and a new action id; it never reopens, reuses, or republishes the terminal action. If fresh preflight finds the requested state already present, the retry becomes the normal persisted completed no-op. Otherwise, it may publish a new command only when current blockers and conflict rules allow it.

Clients submit every first-ship device action through `POST /api/v1/devices/:deviceId/actions` with a closed discriminated body shaped as `{ "type": action_type, "input": action_specific_input }`. The server rejects unknown action types and unknown or invalid input fields; it never accepts a topic, raw MQTT payload, transport QoS, or arbitrary context from the browser. Read-only workflow-specific preflight remains on separate typed endpoints and does not create actions. `GET` on the same `/actions` collection lists history, while the canonical item URL remains `GET /api/v1/devices/:deviceId/actions/:actionId`. First ship does not add a general HTTP idempotency-key protocol. The browser disables an action immediately after submission and never automatically replays state-changing requests; any explicit operator retry is intentionally a new request and action id, governed by fresh no-op and conflict checks. This keeps duplicate semantics aligned with the already accepted action lifecycle instead of adding a second request-deduplication lifetime.

The server reconciles pending deadlines independently of browser polling. A one-second process timer atomically marks every submitted pending action whose `timeout_at` has passed as `timed_out` with `reason_code: "confirmation_timeout"`; conflict checks and canonical action reads also reconcile affected overdue rows before using them so event-loop delay cannot leave stale locks. For a timeout, `completed_at` records the original absolute `timeout_at`, while `updated_at` records when the terminal row was persisted. During startup recovery, submitted actions whose deadlines already passed are timed out before MQTT reconnect; unexpired submitted actions retain their original deadline and confirmation bases. Prepared-but-unsubmitted actions follow the existing interruption rule. Timeout reconciliation uses the persisted server clock boundary and injectable clocks/timers in tests, not a browser timer or a separate job service.

Canonical `action.type` values describe operator or server intent, not MQTT transport operations. The closed first-ship vocabulary is `load_schedule`, `reload_expected_schedule`, `save_as_new_template`, `acknowledge_drift`, `update_outlet_config`, `repair_outlet_label`, `acknowledge_label_drift`, `confirm_device_setup`, `sync_time`, `switch_to_manual`, `return_to_auto`, `set_manual_outlet_state`, `emergency_all_off`, and `run_water_pump_now`. Distinct intents remain separate even when they use the same firmware topic or confirmation mechanism. Generic transport-level types such as `mqtt_publish`, `schedule_write`, and `relay_command` are prohibited. A new first-class device workflow requires an explicit schema addition rather than an arbitrary type string.

First ship does not expose remote editing for timezone, configured time source, SNTP servers, temperature/rH calibration, or firmware OTA. CE accepts configuration writes on `growhub/<MAC>/config` and OTA URLs on `growhub/<MAC>/ota`, but the current public contract does not publish a retained authoritative configuration or OTA result state that Command Center can compare with the requested intent. Those settings remain available through the firmware-local UI, while Command Center supports the separately acknowledged `sync_time` recovery action. Adding remote configuration or OTA later requires a typed Command Center action, a firmware-owned state/error acknowledgement contract, lifecycle and conflict rules, and hardware bench coverage; Command Center must not add a fire-and-forget generic publish path for either topic.

Exactly four first-ship action types are synchronous Command Center-local actions: `save_as_new_template`, `acknowledge_drift`, `acknowledge_label_drift`, and `confirm_device_setup`. They change only Command Center-owned persisted records, never publish MQTT, never depend on broker availability, never enter `pending`, and return HTTP `200` with a completed action whose `timeout_at` is `null`. Every other action type in the closed first-ship vocabulary is MQTT-backed, returns HTTP `202` after transport handoff, and uses the uniform 15-second firmware-confirmation lifecycle unless it resolves as a pre-publish no-op or blocked attempt.

Each synchronous local action commits its domain changes, any resulting device event or episode transition, and its completed action record in one SQLite transaction. For example, Save as new template atomically creates the template and revision, updates the device expectation, reconciles the drift episode, creates the reconciliation event, and records the completed action. If any step fails, Command Center rolls back the entire transaction and returns typed HTTP `500 internal_error` with no action resource or history entry. It never exposes a partially committed local action as `interrupted`.

Mirror-dependent local actions use optimistic concurrency preconditions so they cannot adopt or acknowledge firmware state different from what the operator reviewed. Save as new template submits the displayed normalized schedule-state fingerprint, normalized outlet-state fingerprint, and active drift episode id because adoption reverse-maps the physical schedule through firmware-owned assignments and label snapshots. Acknowledge drift submits the displayed normalized schedule-state fingerprint plus active drift episode id. Acknowledge label drift submits the displayed normalized outlet-state fingerprint plus the affected device mapping identity. Confirm device setup submits the displayed normalized outlet-state fingerprint. The server compares those preconditions to current persisted mirror and episode/mapping state inside the same SQLite transaction before applying domain changes. A mismatch persists a terminal blocked action with `reason_code: "device_state_changed"` and returns HTTP `409 action_blocked`; the operator must review current firmware state and submit a new action. Fingerprints are request preconditions and internal correlation data, not normal action context or Recent activity fields.

A stale local action's blocked context identifies the mismatched precondition through exactly one safe `changed_precondition` value: `schedule_state`, `outlet_state`, `drift_episode`, or `device_mapping`. This allows action details and the immediate conflict UI to distinguish firmware schedule changes, outlet-state changes, replaced or resolved drift episodes, and changed device mappings while retaining the shared `device_state_changed` reason code. The context never exposes submitted, previous, or current fingerprints, raw retained state, or payload diffs.

When a pending action blocks another device action, the UI shows the blocked action as disabled with a specific inline reason and, when possible, a link to the blocking pending action. For example, the schedule load control can show `Load schedule unavailable while Return to AUTO is pending.` Command Center does not silently hide blocked actions or queue conflicting commands.

The server enforces the same pending-action blocks even when the UI already disabled the command, because requests can race, browser tabs can be stale, and future clients may call the API directly. Before returning a blocked response, the server persists the attempted operation as a canonical terminal action with `status: "blocked"`. The endpoint returns HTTP `409 Conflict` using the normal typed error envelope with `error.code: "action_blocked"`. Its allowlisted `error.details.blocked_action` is that full canonical blocked action, including its id, type, terminal timestamps, context, and stable reason code. `error.details.blocking_action` is a compact reference containing id, type, status, created time, and timeout time when present; it is nullable when current device state rather than another pending action caused the block. The UI derives copy such as `Load schedule unavailable while Return to AUTO is pending` from those fields so tests, future clients, and rendering stay consistent. A blocked attempt has no `Location` response header because it is already terminal; `Location` remains reserved for `202 Accepted` pending actions. A request becomes a persisted blocked action only after authentication and authorization succeed, the target device exists, the payload is valid, and the request reaches a final state-changing action endpoint but current device or action state prevents execution. Examples include pending-action conflicts, stale outlet fingerprints, wrong relay mode, an offline device, required retained state still syncing, or required Device setup review. Read-only preflight blockers never create actions. Input validation, authentication, CSRF, unknown-resource, rate-limit, `broker_unavailable`, and `server_shutting_down` failures keep their ordinary `400`, `401/403`, `404`, `429`, or `503` API responses and create no action; failures before the server can persist a trustworthy action record also create no action. `broker_unavailable` is not a conflict between device actions and remains a typed `503`. Other publish or server failures remain `5xx` unless a separate persisted-action rule applies.

Pending device actions are persisted with their intended confirmation criteria, required retained MQTT topic keys, and timeout deadline so they survive a Command Center server restart. For action types whose confirmation depends on comparing retained state against what Command Center published, such as schedule loads and outlet config writes, the pending action also stores the normalized intended payload used for confirmation. Command Center does not need to persist the raw outbound MQTT JSON string for first ship. Actions whose confirmation does not require payload comparison, such as time sync and Return to AUTO, store only the confirmation criteria needed to resolve the action. Required retained topics are stored explicitly on the action as logical device-scoped keys, such as `required_retained_topics: ["schedule/state"]`, `["outlets/state"]`, or `["presence"]`, not full `growhub/<MAC>/...` MQTT strings. The pending action is already scoped to one device, and the server resolves these logical keys to concrete MQTT subscriptions at the integration boundary. This gives restart recovery, `Syncing retained state`, and conflict responses one source of truth instead of hard-coded topic dependencies spread across UI and server logic, while keeping tests and future topic-prefix changes cleaner. On restart, the server rebuilds each device mirror from retained MQTT state, then confirms, rejects, or times out persisted pending actions using the same rules as before restart. Until the retained state needed for an action's confirmation has been received, the action remains pending and blocking; Command Center does not confirm or clear persisted pending actions from stale pre-restart mirror data. Timeout deadlines are absolute and are not extended by server downtime; after retained state is rebuilt, or if the deadline passes before retained state arrives, a pending action is marked timed out if it still cannot be confirmed or rejected. A persisted pending action confirmed from retained state during restart is shown in primary action history as completed normally; diagnostic views may later record that confirmation happened after a server restart. This prevents restarts from losing the reason actions are blocked, incorrectly allowing conflicting commands while firmware state is still catching up, or giving old pending actions a fresh confirmation window.

Command Center keeps a bounded device action history for the first shippable version instead of storing only the current pending action. The canonical history is device-scoped, and auth/admin events are excluded from it. Clients list it through `GET /api/v1/devices/:deviceId/actions?limit=25&cursor=<opaque>`, which returns direct body `{ "actions": [...], "next_cursor": string | null }` ordered newest first. The default limit is 25 and the maximum is 100. Cursor pagination is based internally on the stable `(created_at, id)` ordering tuple, but the cursor itself is opaque and server-validated; page-number pagination is excluded because newly created actions would shift records between pages. An unknown device returns the same typed `404 device_not_found` response as other device-scoped routes. Device pages show a compact Recent activity timeline with user-facing text and timestamps so users can answer what just happened without opening diagnostics. That merged timeline comes from a separate device-scoped `/activity` endpoint and contains a chronological union distinguished by `kind: "action"` or `kind: "device_event"`; canonical action lookup, pending-action polling, and action-history clients continue to use `/actions`. Schedule-load action records include schedule template and schedule template revision references when the action came from a template, and template views can query or filter those device-scoped records to show deployment activity. Action history records user-requested or server-executed device actions only, including recent completed, rejected, timed-out, interrupted, and blocked attempts with normalized action and result fields. It may include local completed device-scoped actions that publish no MQTT, such as setup confirmation and label drift acknowledgement. Informational mirror-derived occurrences, such as schedule drift detected from firmware-owned state and schedule drift later reconciled, are separate `device_event` records rather than fake actions. Device events never create pending actions, require firmware confirmation, block MQTT-backed actions, or imply that Command Center caused the firmware-side change. Stale outlet edit draft choices such as `Reload firmware state`, `Copy changes into a fresh draft`, and `Discard draft` are browser/form workflow and do not create device action history entries. If a stale Apply request reaches the server and is rejected with `outlet_state_changed`, that rejected server request is recorded as a blocked or rejected attempt; the later successful outlet config write is recorded only after Apply publishes and firmware confirms through retained `outlets/state`. When a confirmed outlet config write refreshes Device setup review, that completed outlet config history record carries metadata such as reviewed timestamp, outlet-state fingerprint, and review-refreshed flag instead of creating a second `setup-confirmed` entry. The current device mirror stores the current schedule drift reason when the device is drifted so device pages can render present-tense copy and remediation prompts without searching activity history. If later retained state refines an already-drifted device from `unknown_firmware_change` to a more specific reason, Command Center updates only the current device mirror reason. Drift device-event records store normalized event metadata, such as expected template and revision, device id, detected timestamp, schedule drift reason snapshot when known, and affected outlet or role summaries when available. First-ship schedule drift reasons are `firmware_schedule_cleared`, `outlet_assignment_changed`, `schedule_body_changed`, and `unknown_firmware_change`; the UI treats them as best-effort explanation, not proof. They do not store raw expected or firmware schedule payload snapshots, and Command Center does not persist rendered human-readable drift diff text. Command Center persists one active drift episode when a device transitions from aligned to drifted, including its `schedule_drift_detected` event id and expected-schedule fingerprint. Repeated retained messages and retained-state rebuild after server restart do not create another detection event while that episode remains active. Reason refinement updates only the current mirror and does not mutate or append to the episode's historical detection event. Reconciliation normally occurs when the firmware-owned active schedule and Command Center's persisted expected schedule are equal under the same normalized schedule-fingerprint comparison. This can happen when a confirmed Reload expected schedule action restores the expected payload, Save as new template establishes a new expected schedule from the still-current firmware state, or a local firmware change independently returns to the previously expected schedule. Explicit Acknowledge drift is the non-equality reconciliation path: it removes the device's expected active schedule and template link while preserving prior load history. The first reconciliation transition creates exactly one `schedule_drift_reconciled` event whose context references the detection event id and carries one closed `resolution`: `loaded_expected_schedule`, `adopted_firmware_schedule`, `firmware_returned_to_expected`, or `acknowledged_drift`. It also includes the related `action_id` when a Command Center action caused reconciliation, then closes the episode. Repeated aligned or unlinked state creates no additional reconciliation event. Entering AUTO, reconnecting, or receiving a newer firmware timestamp does not reconcile drift without normalized schedule equality or explicit acknowledgement. A later linked aligned-to-drifted transition creates a new episode and new event id. The canonical operator terms are Reload expected schedule, Save as new template, and Acknowledge drift; Command Center does not expose a separate ambiguous Adopt firmware schedule action. When a firmware error resolves an action, the history stores the relevant stable error reason snapshot, but not full raw MQTT payload snapshots. Current raw retained MQTT state, current mirror snapshots, generated full schedule diffs, and MQTT-level details remain in diagnostic views, not the compact recent activity UI. First ship does not persist historical raw MQTT payload snapshots; diagnostics shows the latest retained raw payloads/current mirror, bounded normalized action and error history, and generated diffs from current mirrored state plus stored expected schedules. First ship includes a minimal authenticated diagnostics/developer path for this raw troubleshooting data, separate from normal device pages and clearly marked as diagnostics. It uses the existing authenticated admin session and does not introduce separate diagnostic roles or permissions for first ship; the diagnostics entry point should stay out of primary navigation so it does not look like a routine operator workflow. It can be low-polish, but it must expose retained MQTT state, compiled Command Center payloads, mirrored firmware active schedule state, payload-level drift/debug diffs, fingerprints, retained timestamps, recent device actions, published MQTT topics, and stable firmware/server rejection reasons without requiring SSH or database inspection. The diagnostics/developer path is strictly read-only for first ship: it can display and copy diagnostic data, but it cannot publish arbitrary MQTT, replay retained messages, mutate mirrored state, or bypass typed device-action endpoints. Disabled UI controls and inline blocked-action reasons do not create history records by themselves. A blocked attempt is recorded only when a command request reaches the server and the server rejects it with `409 Conflict`; no MQTT command is published, but the record explains why the server refused the action. Broker-unavailable attempts return `503 Service Unavailable` instead and are excluded because they are global server connectivity failures rather than device-scoped decisions; diagnostics/server health records them. Command Center does not maintain a separate template action-history model for first ship because that would duplicate lifecycle state and make schedule-load confirmation harder to reason about. This is not a full audit log; unresolved pending actions are kept until they resolve, and terminal records are bounded by both count and age, such as the latest 100 records per device and no more than 30 days.

A canonical `device_event` contains `id`, `device_id`, `type`, `occurred_at`, and an allowlisted immutable `context` object when applicable. Its opaque id is a lowercase UUID v4 generated with `crypto.randomUUID()` and provides stable identity, ordering, and deduplication support. The closed first-ship event types are `schedule_drift_detected` and `schedule_drift_reconciled`. Event context may capture the expected template and revision, drift reason snapshot, affected outlet or role summaries, and the originating detection event id on reconciliation. Reconciliation context also carries the closed `resolution` and related Command Center `action_id` when applicable. It does not contain raw retained state, MQTT payloads, generated schedule diffs, or arbitrary keys. Device events do not borrow action lifecycle fields such as `status`, `timeout_at`, `completed_at`, or `reason_code`. Device-event retention is bounded independently from action history: a record remains only while it is both among the latest 100 device events for that device and no older than 30 days. Normal maintenance and startup cleanup prune older or excess events. Activity cursors do not preserve source records past that policy, while unresolved pending actions remain governed by their separate action-lifecycle retention rule. The computed timeline can therefore draw from at most 100 retained terminal/local action records plus 100 retained device events per device, subject to each model's age policy, in addition to unresolved pending actions.

Clients read the merged timeline through `GET /api/v1/devices/:deviceId/activity?limit=25&cursor=<opaque>`, which returns `{ "activity": [...], "next_cursor": string | null }` newest first. Each item is a discriminated union: an action item contains `kind: "action"`, an activity-level `occurred_at`, and the canonical `action`; a device-event item contains `kind: "device_event"`, `occurred_at`, and the canonical `device_event`. An action's activity timestamp is permanently its `created_at`, so later pending-to-terminal updates change the embedded action but never move the timeline item. Device events use their own `occurred_at`. The stable merged ordering tuple is `(occurred_at, kind, id)` behind an opaque server-validated cursor. The endpoint defaults to 25 items, accepts at most 100, and returns typed `404 device_not_found` for an unknown device. Command Center computes this union from persisted actions and device events and does not persist a third duplicate activity-record model.

Current-state warnings such as `Device state not received` remain current device state and do not create device action history entries.

First-ship diagnostics has two read-only scopes. Device-scoped diagnostics show per-device current retained MQTT state, compiled Command Center payloads, mirrored firmware active schedule state, generated payload-level drift/debug diffs, fingerprints, retained timestamps, bounded retained-state incidents, recent normalized device actions, published MQTT topics, and stable firmware/server rejection reasons. Retained-state incidents are scoped to one device and one logical retained key, such as `outlets/state` or `schedule/state`, because different retained states can resolve at different times and unblock different workflows. Persisted retained-state incident records store the device id and logical retained key, not the concrete MQTT topic string; diagnostics display and bundle export derive the full `growhub/<MAC>/...` topic from those values at the integration boundary. Missing retained state is not persisted as a retained-state incident while it is still inside the 60-second `Syncing retained state` grace period. That grace period is started by proactive mirror rebuild for known devices during Command Center server startup or MQTT broker reconnect after the server has connected and completed required subscriptions, not by the first UI read or attempted device action. When the broker is disconnected, diagnostics shows the broker/server connection problem and paused retained-state rebuild rather than creating or aging active retained-state incidents for each device. During that pre-escalation window, diagnostics may show retained-state rebuild status, pending dependencies, and latest retained timestamps, but not an active retained-state incident row for that missing key. Active retained-state incidents are tracked separately from resolved incident history only after the missing-state condition crosses that threshold and becomes `Device state not received`. Retained-state incident `started_at`, `resolved_at`, and duration use the Command Center server clock because the incident describes server-observed missing retained state, not firmware wall time or MQTT payload time; if the condition crosses the threshold, `started_at` remains the original server-observed missing-state start time. Resolved retained-state incidents are kept only while they are both within the latest 50 resolved incidents for that device and no older than 30 days; older or excess records are pruned. Global diagnostics stays small and shows server/broker health, server MQTT connection status, subscription readiness, last broker connect/disconnect timestamps, redacted last broker error, retained-state rebuild status, pending action counts, bounded auth/security event history, and recent server-side errors. Authenticated on-screen diagnostics may show the exact stored client IP addresses and normalized admin username for local troubleshooting; export applies the stronger redaction rules described below. Command Center does not include a broker-wide topic explorer in first ship because that would turn diagnostics into a general MQTT inspection tool instead of focused troubleshooting support for the typed device-action model.

Diagnostics is the only first-ship API surface that exposes full retained-state incident records, active/resolved incident history, logical retained keys, and derived concrete MQTT topics.

First ship also includes a read-only diagnostics bundle export for current device diagnostics and global diagnostics. The bundle is one redacted JSON document, not a ZIP or archive. It uses stable top-level sections such as `meta`, `global`, `device`, `retained`, `expectedSchedules`, `diffs`, `retainedStateIncidents`, `recentHistory`, and `authSecurityEvents` so it is easy to inspect, attach to an issue, and test. The `retainedStateIncidents` section contains separate `active` and `resolved` arrays instead of one mixed list: active incidents include `started_at` and elapsed duration, while resolved incidents include `started_at`, `resolved_at`, and final duration. The bundle contains the same current diagnostic data available on screen: current retained payloads, current mirror state including current sensor values and device health warnings, compiled and expected schedules, generated diffs, bounded retained-state incident metadata, normalized recent action and error history, bounded redacted auth/security events, and server health metadata. Exported `authSecurityEvents` never contain raw client IP addresses or the configured admin username. During each export, every unique client IP is replaced consistently within that bundle by an opaque alias such as `client-1`, preserving event correlation without revealing the address. Aliases are regenerated independently for each export, no alias-to-address mapping is included in the bundle or persisted, and first ship does not offer an option to include raw client addresses. Any stored normalized admin identity is replaced with the fixed value `admin`; because first ship has exactly one administrator, the event type preserves the useful meaning of login and username-change events without exposing the configured username. First ship does not offer an option to include the configured username. It does not include recent sensor measurement history for first ship; sensor-history export remains part of the existing data/CSV workflow or a separate future export. It includes device MAC addresses and full device-scoped MQTT topic names by default because those identifiers are needed to correlate retained state, CE firmware logs, and support reports; retained-state incident topics are derived for export rather than persisted on the incident record. The export UI must clearly label that the bundle contains local device identifiers before download. The bundle does not include a historical raw MQTT payload stream, passwords, raw credentials, session ids, CSRF tokens, authentication tokens, MQTT credentials, Wi-Fi credentials, environment secrets, or other sensitive configuration. Exporting the bundle does not create a device action, publish MQTT, mutate mirror state, or turn diagnostics into an audit log. A multi-file archive can be added later if diagnostics need binary files, logs, or large attachments.

These diagnostics boundaries are sufficient for first ship. Additional diagnostics features are deferred unless implementation or bench testing reveals a blocking troubleshooting gap.

When retained state required for restart recovery has not arrived yet, affected device views and actions show `Syncing retained state` and keep blocked actions disabled with the same pending-action conflict reason. Syncing retained state is scoped to the missing retained topic and affected actions rather than making the whole device unusable; a device summary signal or device-level banner may summarize that required retained state is still syncing during startup or reconnect. The grace timer starts proactively for each known device's required retained states when Command Center starts or reconnects to MQTT after the broker connection and required subscriptions are active, so warning timing does not depend on which browser page the user opens first. While Command Center is disconnected from the broker, per-device retained-state escalation is paused and the UI shows the global broker/server connection problem instead. After required retained state has been mirrored, broader summary/banners clear and any narrower sync state remains inline only on affected actions or views. If required retained state arrives before the 60-second grace period expires, the sync state clears without creating a retained-state incident. If required retained state is still missing after the 60-second grace period, Command Center escalates the condition to Needs attention as `Device state not received` while keeping affected actions disabled until the required state arrives. Multiple missing retained keys on one device are represented as separate retained-state incidents in diagnostics, but normal user-facing surfaces aggregate them into one device warning with friendly missing-state summaries rather than raw topic lists. This escalation is current-state only and does not create a device action history entry. When a missing retained state later arrives and the device mirror is current for that logical key, its retained-state incident resolves independently; the broader `Device state not received` warning clears only after all escalated required retained keys for that device have resolved. The warning is not user-dismissible and clears only from current mirror state when all escalated required retained categories arrive. Diagnostics retains bounded retained-state incident records with device id, missing logical retained key, server-observed started time, server-observed resolved time, and duration. The retained-state incident start time is the original server-observed missing-state start time, not the 60-second escalation time. Active incidents are visible separately while unresolved, and resolved incidents are pruned to the latest 50 per device and no more than 30 days. Normal UI names the missing state by workflow or state category, while diagnostics exposes when the missing-state condition began plus the logical retained key and derived concrete MQTT topic for troubleshooting. Read-only views and unrelated actions can use whatever current state is available. If persisted drift state exists but retained `schedule/state` is missing or still syncing, Command Center may show the schedule drift banner from persisted drift metadata but disables drift `View details` until the retained schedule state is current, because the generated diff depends on the latest mirrored firmware active schedule. Drift acknowledgement and schedule adoption actions are also visible but disabled while retained `schedule/state` is missing or syncing, because those actions change Command Center's expectation/linking state and must be based on current firmware-owned active schedule state. Command Center does not show the device as offline solely because retained state is still syncing or because the broker is unavailable; offline remains driven by firmware presence state. Once presence state is known, offline is represented as `device_offline`, not `presence_state` or `device_state_not_received`.

For normal device detail, this retained-state condition is exposed as one aggregate current warning with code `device_state_not_received` plus the affected friendly state categories from the shared retained-state category enum. The warning record does not include dismiss or acknowledge action availability. Individual disabled actions that are blocked by retained-state sync carry their own `missing_states` context with the complete subset of friendly state categories still needed by that action, sorted in enum order. The normal detail response does not include full incident rows, per-key diagnostic history, separate per-retained-key warning codes, concrete MQTT topic strings for retained-state incidents, or global server-health banner state such as active broker outage. MQTT-backed action availability may still include `broker_unavailable` as an action-level disabled reason.

The server computes typed drift recovery action availability from the current device mirror and persisted drift state as part of the normal device detail response, not from a separate availability endpoint. The availability payload is an object keyed by stable action key, not an array, so rendering and tests do not depend on response ordering. The payload always includes all four drift recovery action keys, even when an action is not visible. The UI hides entries where `visible` is false, but a missing key is treated as a server contract problem rather than an intentional hidden action. The first stable drift recovery action keys are `view_drift_details`, `reload_expected_schedule`, `save_as_new_template`, and `acknowledge_drift`; display labels such as `View details`, `Reload expected schedule`, `Save as new template`, and `Acknowledge drift` are UI copy and can change without changing the server contract. The initial visibility rule is that all four drift recovery actions are visible only when the current device mirror is drifted. When the device is not drifted, all four keys are still present with `visible: false`, `enabled: false`, and `disabled_reason: not_drifted`. For each action, the server returns `visible`, `enabled`, and a nullable single primary `disabled_reason`. If several blockers apply, the server chooses the highest-priority reason for that action so UI copy and tests stay deterministic; optional structured context may accompany the reason, such as the blocking pending action id or `missing_states` values from the shared retained-state category enum. The first stable disabled reason code set is `broker_unavailable`, `retained_state_syncing`, `device_offline`, `pending_action_conflict`, `not_drifted`, `not_adoptable`, `missing_expected_schedule`, and `unsupported_firmware_schedule`. When an action is disabled by `retained_state_syncing`, its structured context includes every friendly state category still needed by that action, sorted in enum order, such as `["schedule_state"]` for drift details or `["outlet_state", "schedule_state"]` for schedule publishing. `view_drift_details` is read-only and does not use `broker_unavailable`, `device_offline`, or `pending_action_conflict` as disabled reasons; when drifted, it requires current retained `schedule/state` and the stored expected active schedule, using `retained_state_syncing` or `missing_expected_schedule` when either input is unavailable. The `View details` endpoint rechecks these same inputs when called and generates the human-readable diff from the latest mirrored firmware schedule plus the stored expected active schedule at view time. It returns only compact diagnostic metadata needed for explainability, such as comparison ids, retained timestamps, fingerprints, and stable reason codes; raw retained MQTT payloads, raw compiled CE schedule JSON, and full payload-level diffs stay behind diagnostics or developer detail. `reload_expected_schedule` is a schedule-publishing action and uses the same safety inputs as schedule loading: broker availability, firmware presence, current retained `outlets/state`, current retained `schedule/state`, and the stored expected active schedule. It uses `broker_unavailable`, `device_offline`, `retained_state_syncing`, `pending_action_conflict`, or `missing_expected_schedule` when those inputs or action state are unavailable. `save_as_new_template` is a local adoption action and does not use `broker_unavailable` or `device_offline` as disabled reasons; when drifted, it requires current retained `schedule/state` and an adoptable firmware active schedule, using `retained_state_syncing`, `pending_action_conflict`, `not_adoptable`, or `unsupported_firmware_schedule` when adoption cannot proceed. `acknowledge_drift` is a local reconciliation action and does not use `broker_unavailable` or `device_offline` as disabled reasons; when drifted, it requires current retained `schedule/state`, using `retained_state_syncing` when retained schedule state is unavailable and `pending_action_conflict` when another pending device action makes expectation changes unsafe. For MQTT-backed actions, `broker_unavailable` is the highest-priority disabled reason because the server cannot publish or confirm commands through MQTT. For actions that can be disabled by pending actions after broker availability is satisfied, the first priority order is `pending_action_conflict`, then `retained_state_syncing`, then `device_offline`, then action-specific state reasons such as `not_drifted` or `missing_expected_schedule`, then action-specific eligibility reasons such as `not_adoptable` or `unsupported_firmware_schedule`. Pending-action conflicts take precedence for state-changing drift recovery actions after broker availability because overlapping device actions are the most immediate safety and attribution issue. The browser renders those states and derives user-facing copy; it does not reimplement broker availability, retained-state sync, offline presence, pending-action conflicts, schedule-load preflight eligibility, adoption eligibility, or drift-linking rules. Device-action endpoints still enforce the same rules server-side when requests arrive, because browser state can be stale or bypassed.

For the first shippable version, schedule-template editing may use the last mirrored outlet state, but schedule loading requires broker availability, current firmware presence, retained `outlets/state`, retained `schedule/state`, and current Device setup review for the retained outlet state. Reloading an expected schedule from drift recovery is treated as a normal schedule load and uses the same preflight requirements. If the broker is unavailable, the device is offline by firmware presence, the retained outlet or schedule state required for preflight is missing or still syncing, or Device setup review is missing or stale, the server rejects the load action instead of publishing MQTT. The UI may keep reload/load actions visible, but disables them with the appropriate reason, such as broker-connection copy for `broker_unavailable`, `Syncing retained state` for missing retained preflight state, device-offline copy for missing firmware presence, or Device setup review copy for stale outlet review. Schedule-load failures caused by missing or stale Device setup review use the top-level blocker code `device_setup_review_required`; when review is blocked by an outlet label conflict, the response may include structured context such as `review_blocked_by: "outlet_label_conflict"`, but the schedule-load blocker remains `device_setup_review_required`. Command Center does not queue schedule loads for unavailable broker connections, offline devices, or compile from only a previously mirrored outlet state, because stale assignments and delayed firmware consumption would make confirmation and user feedback ambiguous.

When a schedule-load request reaches the server, the server recomputes preflight against the current device mirror instead of trusting the warning list or compile result previously shown by the browser. Browser confirmation records the user's intent to continue through warnings, not permission to publish from stale state. If recomputed preflight has blockers, the server rejects the load without publishing MQTT. If the warning set changed since the user's confirmation, the server returns the updated warnings so the UI can ask again. If the warning set is unchanged or has cleared, and no blockers or conflicting pending actions exist, the server may compile and publish the schedule.

Schedule-load preflight responses use typed blocker and warning records, not display-only strings. Each record has a stable code, a blocking or warning classification, and affected entity identifiers such as template role id, physical outlet id, assignment, label, firmware warning code, blocking action id, or complete `missing_states` values from the shared retained-state category enum when retained state is syncing. The UI derives user-facing copy from those records. Server comparison of a previously confirmed warning set uses normalized stable code plus affected entity identity, not localized text or response order. Initial preflight codes include blockers such as `broker_unavailable`, `missing_assignment`, `ambiguous_assignment`, `incompatible_assignment`, `template_role_duplicate`, `template_role_none`, `device_offline`, `retained_state_syncing`, `device_setup_review_required`, and `pending_action_conflict`, plus warnings such as `label_drift`, `extra_assigned_outlet`, `active_entry_will_be_removed`, `schedule_drift_will_be_replaced`, `time_invalid`, and `sensor_unavailable`.

Schedule-load preflight is exposed through its own typed server endpoint separate from the final load action. The preflight endpoint is read-only from the firmware perspective: it does not publish MQTT, does not create a pending device action, and does not replace the expected active schedule. It returns HTTP `200 OK` with typed blockers, warnings, remediation actions, inferred role mappings, and any preview data needed by the browser, including a `broker_unavailable` blocker when the broker is unavailable. The browser uses this endpoint to render schedule-load review, but it does not reimplement schedule matching or compile rules. The normal schedule-load review shows a human-readable compiled schedule preview with role-to-outlet mapping and schedule summaries, such as `Canopy Light -> Outlet 1, 06:00-18:00`, rather than raw CE JSON. The exact compiled CE payload remains available in diagnostics or developer detail because it is the payload used for publish, confirmation, and drift comparison. The final load endpoint still recomputes preflight from the current device mirror before publishing, so a prior successful preflight response is not treated as authorization to load stale state.

Schedule-changing actions are serialized per device in the first shippable version. If a pending schedule-changing action already exists for a device, the server rejects another schedule-changing action until the device mirror confirms, rejects, or times out the pending action.

Outlet configuration actions are also serialized per device and conflict with schedule loads because schedule preflight depends on current retained outlet state. If a pending outlet config action exists, the server rejects schedule load actions until the device mirror confirms, rejects, or times out the outlet config action; if a pending schedule load exists, the server rejects outlet config actions such as outlet label repair. Outlet configuration writes require broker availability, current firmware presence, and retained `outlets/state`; when the broker is unavailable, the device is offline, or retained outlet state is still syncing, the UI disables Apply and the server rejects the request with `broker_unavailable`, `device_offline`, or `retained_state_syncing`. Each outlet config write is based on a retained outlet-state fingerprint. Before publishing, the server compares the request's base fingerprint to the current retained outlet-state fingerprint and rejects stale drafts with `outlet_state_changed` instead of publishing MQTT. Command Center does not queue outlet config writes because `outlets/config` is a full replacement and applying it later from stale state could overwrite firmware-side changes made locally.

Pending outlet config actions use the uniform 15-second confirmation deadline measured from MQTT handoff. They clear only when a newer retained outlet-state revision reflects the intended full outlet config. Only a newer matching same-device `outlets/error` rejects that pending action. Schedule errors, time errors, health warnings, presence changes, and retained `schedule/state` changes update the device mirror but do not reject the pending outlet config action. If neither matching newer retained outlet state nor a matching outlet error arrives before the deadline, the server marks the pending outlet config action timed out and does not retry automatically.

If a later retained `outlets/state` matches a timed-out outlet config action's intended config, the device mirror still updates to the firmware-owned state, but the old action history remains timed out. Command Center does not retroactively convert timed-out outlet config actions to success because retained MQTT messages do not carry request IDs.

Command Center allows outlet assignment and label edits while the device mirror shows MANUAL mode, as long as no conflicting pending action exists. Label-only edits are routine outlet config actions that may create or resolve label drift, but they do not clear role mappings while the physical outlet and assignment remain unchanged. Assignment-changing edits use the same full replacement outlet config action flow, with UI copy explaining that the edit changes firmware-owned outlet identity and schedule validity, not the current relay outputs. When firmware confirms the new outlet state, Command Center mirrors the resulting outlet assignments, labels, and schedule changes, clears affected role mappings as needed, and leaves the device in MANUAL with relay outputs represented as mirrored runtime state. The UI warns that returning to AUTO can leave newly assigned outlets unscheduled until a schedule template is loaded or the active firmware schedule is adopted.

When label drift exists, Command Center offers two explicit resolution paths. `Outlet label repair` publishes an outlet config update so CE firmware renames the physical outlet back to the expected mapped label. `Label drift acknowledgement` accepts the current firmware-owned label for that device mapping only, updates the device mapping's expected label snapshot to that firmware label, clears label drift locally, publishes no MQTT, does not rename the firmware outlet, does not mutate the reusable schedule template, and does not affect schedule validity. Future firmware label changes are compared against the acknowledged device-specific label. It is recorded as a local completed device action history entry, not a pending device action.

When Command Center detects an outlet label conflict, Device setup may suggest replacement labels such as `Exhaust Fan 1` and `Exhaust Fan 2`, but suggestions are not applied automatically. Suggested labels are deterministic: Command Center sorts the conflicting physical outlet IDs ascending and appends `1`, `2`, and so on in that order, so suggestions do not reshuffle between refreshes. The user may edit the suggested labels before applying them. The user must explicitly apply the chosen labels through the normal full outlet-config write flow, and Command Center waits for retained `outlets/state` confirmation before treating the conflict as resolved. Until the conflict is resolved, `Confirm current setup` stays disabled and schedule loading remains blocked by missing current Device setup review. Duplicate labels on outlets assigned `None` are not outlet label conflicts and do not block confirmation. Command Center never silently renames firmware-owned outlets to repair an outlet label conflict.

Command Center also allows assignment-changing outlet edits while the device mirror shows AUTO mode, as long as no conflicting pending action exists, but requires explicit confirmation copy before publishing the full replacement outlet config. The confirmation explains that CE firmware may clear affected active schedule entries and immediately re-evaluate relays in AUTO. After firmware confirms, Command Center mirrors the new firmware-owned outlet state and schedule state, shows schedule drift or unscheduled outlets when the retained active schedule no longer matches the expected template deployment, and guides the user to Reload expected schedule, Save as new template, or Acknowledge drift instead of pretending the old template still fully applies.

Pending schedule loads use the uniform 15-second confirmation deadline measured from MQTT handoff instead of automatic retry. They clear only when a newer retained `schedule/state` revision contains a normalized active schedule body that matches the compiled physical schedule Command Center published. Relay mode, outlet status, warnings, time health, and firmware source fields are mirrored as device state but are not part of schedule-load confirmation. Only a newer matching schedule-write error from the same device rejects that pending load. Time warnings, sensor warnings, outlet config errors, time action errors, presence changes, and routine health warnings update the device mirror but do not reject the pending load. When the deadline elapses without matching newer retained state or a matching schedule-write error, the server marks the pending action timed out, keeps the previous expected active schedule, and preserves any existing schedule drift.

If a later retained `schedule/state` exactly matches a timed-out schedule load, the device mirror still updates to the firmware-owned active schedule, but the old action history remains timed out and Command Center does not automatically replace the expected active schedule from that timed-out action. The first shippable version does not include an explicit recovery action for this case; one can be added later if bench testing shows delayed confirmations are common enough to need first-class handling.

MQTT time sync is tracked as a pending device action, but not as a schedule-changing action because it does not alter the active schedule body. It confirms only when a newer retained `schedule/state` reports `source: "time"` and `time_valid: true`, rejects on a newer valid same-device `time/error` for `time/action`, and times out without automatic retry. Because a successful time sync can cause CE firmware to re-evaluate relays in AUTO mode, the UI presents it as a real pending action instead of a fire-and-forget command.

While a time sync action is pending, Command Center may still run schedule preflight, but it blocks the final schedule load action until the time sync confirms, rejects, or times out. This avoids overlapping a schedule publish with pending wall-time recovery that may change AUTO relay evaluation and health warnings.

While a time sync action is pending, Command Center allows read-only refreshes but rejects routine relay mode changes and direct outlet controls until the time sync confirms, rejects, or times out. Time sync can trigger AUTO relay evaluation, so overlapping it with manual relay commands makes the UI harder to explain. Emergency all-off remains a separate explicit exception that must be handled deliberately instead of treating all direct controls as safe during pending time sync.

While a time sync action is pending, Command Center also rejects assignment-changing outlet config actions until the time sync confirms, rejects, or times out. Assignment changes can clear schedule entries and trigger AUTO relay evaluation, so overlapping them with wall-time recovery makes device feedback harder to reason about. Label-only outlet repairs may proceed while time sync is pending because they do not affect firmware schedule validation, active schedule entries, or relay behavior.

While an assignment-changing outlet config action is pending, Command Center rejects routine time sync actions until the outlet config action confirms, rejects, or times out. A pending label-only outlet repair does not block time sync because label repair confirms through retained `outlets/state`, time sync confirms through retained `schedule/state`, and label-only changes do not affect schedule validation, active schedule entries, or relay behavior.

While an assignment-changing outlet config action is pending, Command Center rejects Return to AUTO actions until the outlet config action confirms, rejects, or times out. Accepted assignment changes can clear schedule entries and affect AUTO evaluation, so Return to AUTO must wait for the firmware-owned outlet state to resolve first. A pending label-only outlet repair does not block Return to AUTO because label-only changes do not affect schedule validation, active schedule entries, or relay behavior.

While a schedule load is pending, Command Center rejects routine time sync actions until the schedule load confirms, rejects, or times out. Time sync confirmation also arrives through retained `schedule/state`, so overlapping it with schedule-load confirmation would make user feedback and action attribution harder to explain. Emergency or recovery-specific exceptions can be considered later, but they are not part of the first shippable version.

Non-schedule-changing actions are still gated when a schedule load is pending if they can confuse confirmation or relay state. Read-only refreshes and unrelated health actions are allowed; routine relay mode changes, including Return to AUTO, and direct outlet controls are rejected until the pending load confirms, rejects, times out, or is interrupted. Emergency all-off is the only first-shippable relay-mode exception while a schedule load is pending.

Emergency all-off is always allowed for the target device, regardless of pending schedule load, Pump Run Now, relay-control action, time sync, or outlet config action. Command Center publishes the firmware manual/all-off command, marks any pending schedule load, Pump Run Now, or relay-control action as interrupted, immediately refreshes the device mirror, and leaves pending time sync or outlet config actions to resolve from their own retained state, firmware error, or local timeout. Emergency all-off supersedes pending manual toggles and pump actions, so Command Center does not later convert an interrupted action to success even if retained state briefly matches its old predicate. Emergency all-off mirrors relay mode and outlet state changes, but it does not change the expected active schedule, mutate template deployment state, or mark schedule drift by itself because the firmware active schedule body may be unchanged. Emergency all-off does not pretend to cancel MQTT messages already published because CE firmware has no request cancellation contract.

After emergency all-off, Command Center shows the device as being in a device-level manual/off state and offers a `Return to AUTO` action. Return to AUTO does not reload a schedule automatically. If the firmware active schedule body still matches the expected active schedule, returning to AUTO resumes that expected schedule. If schedule drift exists, Return to AUTO is still allowed but must show explicit drift context: firmware AUTO will run the current firmware-owned active schedule, not necessarily the Command Center template. Command Center keeps Reload expected schedule, Save as new template, and Acknowledge drift visible before and after Return to AUTO so the user can resync or accept the drift explicitly.

Return to AUTO is tracked as a pending relay-mode device action, not as a schedule-changing action. If the device mirror already shows AUTO mode and no conflicting pending action exists, Return to AUTO returns and persists an immediate completed no-op action without publishing MQTT or creating pending state. Any schedule drift, warnings, or active template state remain unchanged and visible. Otherwise, Return to AUTO confirms when retained firmware state shows the device is back in AUTO, rejects on a same-device firmware error for that relay-mode action if CE firmware publishes one, and times out locally without automatic retry. Return to AUTO does not change the expected active schedule or template deployment state.

When retained firmware schedule state reports device health warnings, Return to AUTO requires explicit user confirmation before Command Center publishes the relay-mode command. Returning to AUTO can immediately change relay outputs, so warnings such as invalid wall time, unhealthy SNTP sync, or unavailable sensor data must be shown in a warning summary with a deliberate `Return Anyway` action. Remediable warnings should expose their remediation action from the same confirmation flow when available, such as `Sync Time First` for invalid wall time. If the user remediates a warning, Command Center waits for retained firmware state to confirm the remediation before offering Return to AUTO again.

When a Return to AUTO request reaches the server after browser confirmation, the server rechecks the current device mirror instead of trusting the warning list previously shown by the browser. Browser confirmation records the user's intent to continue through warnings, not permission to publish from stale state. The server rechecks pending-action conflicts, current relay mode, retained schedule state, and current device health warnings before publishing. If new blockers exist, the server rejects the action without publishing MQTT. If the warning set changed since the user's confirmation, the server returns the updated warnings so the UI can ask again. If the warning set is unchanged or has cleared, and no blockers or conflicting pending actions exist, the server may publish Return to AUTO.

The first shippable version includes routine manual relay controls, including `Switch to MANUAL` and per-outlet manual triggering, but treats them as first-class device actions rather than fire-and-forget MQTT publishes. If the device mirror already shows MANUAL mode and no conflicting pending action exists, `Switch to MANUAL` returns and persists an immediate completed no-op action without publishing MQTT or creating pending state. Otherwise, `Switch to MANUAL` publishes `"2"` to `control/mode`, preserves current relay outputs according to the CE firmware contract, creates pending relay-mode action state, confirms when retained firmware state shows MANUAL mode, times out locally without automatic retry, and appears in device action history. Command Center does not require relay outputs to match a captured pre-switch output snapshot before confirming Switch to MANUAL, because retained relay state may have been stale or changed just before the command; relay outputs remain mirrored runtime state. Per-outlet manual triggering is available only when Command Center's device mirror shows the device in MANUAL mode. Physical outlets whose firmware-owned assignment is None remain visible in the relay list, but their manual toggles are disabled with an assignment-required reason; normal device control does not offer raw hardware toggling for unassigned outlets, and first ship does not include a diagnostics or admin exception for raw relay testing. The browser sends a semantic request such as `{ outletId, desiredState }` to a typed server endpoint; the server computes the intended full firmware relay bitmask from the current device mirror. If the requested outlet already has the desired state in the current mirror and the computed bitmask matches the mirrored bitmask, the server returns and persists an immediate completed no-op action without publishing MQTT or creating pending state. Otherwise, the server stores the intended bitmask on the pending relay-control action for confirmation, publishes it to `control/relay`, confirms only when retained firmware state shows MANUAL mode and mirrored relay outputs match the intended full bitmask, rejects on same-device `control/error`, times out locally without automatic retry, and records the action in device action history. This prevents Command Center from marking a relay-control action successful after the device has already returned to AUTO or when outputs do not match what Command Center published. If the required retained relay state is missing or still syncing, the server rejects the request instead of guessing the other outlet states. When the device mirror shows AUTO, direct outlet toggles remain disabled until the user explicitly runs `Switch to MANUAL` and that pending action confirms. Command Center does not offer a first-shippable composite action that both switches to MANUAL and applies an outlet change, because switching to MANUAL pauses automation and must be visible as its own deliberate action. If the UI or server cannot support that model for a routine manual relay control, that control is not shipped as an optimistic shortcut. The generic MQTT publish endpoint is not a first-shippable UI path for manual relay controls.

Per-outlet manual triggering changes runtime relay outputs in MANUAL mode only. It does not change the firmware active schedule body, replace the expected active schedule, mutate template deployment state, or mark schedule drift. Command Center shows MANUAL mode, the mirrored relay state, and recent relay-control action history; when the user returns to AUTO, firmware re-evaluates the existing active schedule.

Switch to MANUAL is disabled in the UI and rejected by the server while a schedule load, time sync, assignment-changing outlet config, or Return to AUTO action is pending. A pending label-only outlet repair does not block Switch to MANUAL because label repair confirms through retained `outlets/state` and does not change assignments, active schedule entries, relay mode, or relay outputs. Switch to MANUAL preserves current relay outputs and changes relay mode, so overlapping it with the blocked pending actions would make confirmation and relay behavior ambiguous. Emergency all-off remains the urgent intervention path while those actions are pending.

Pending relay-control actions are serialized per device. While a relay-control action is pending, Command Center disables and server-rejects additional per-outlet toggles, Return to AUTO, schedule loads, and assignment-changing outlet config until the pending action confirms, rejects, or times out. Emergency all-off remains allowed. Time sync and label-only outlet repair may proceed while relay-control is pending because MANUAL mode relay-control does not depend on wall-time evaluation or outlet labels, and those actions do not change relay outputs, relay mode, assignments, or active schedule entries. This avoids computing a second full relay bitmask from stale relay state, prevents schedule or assignment changes from moving the meaning of the outlet state being manipulated, and keeps device action history understandable.

While a Return to AUTO action is pending, Command Center may still run schedule preflight, but it blocks the final schedule load action until Return to AUTO confirms, rejects, or times out. Return to AUTO can immediately trigger CE firmware AUTO evaluation and relay state changes, so overlapping it with a schedule publish makes confirmation and user feedback harder to reason about.

While a Return to AUTO action is pending, Command Center rejects routine time sync actions until Return to AUTO confirms, rejects, or times out. Return to AUTO can trigger AUTO relay evaluation, and time sync can also trigger schedule evaluation once wall time becomes healthy, so overlapping them would make relay changes and confirmation feedback harder to explain. Emergency all-off remains the explicit exception.

While a Return to AUTO action is pending, Command Center rejects assignment-changing outlet config actions until Return to AUTO confirms, rejects, or times out. Assignment changes can clear schedule entries and affect AUTO evaluation, so they should not overlap with a pending return to automation. Label-only outlet repairs may proceed because they confirm through retained `outlets/state` and do not affect schedule validation, active schedule entries, or relay behavior.
